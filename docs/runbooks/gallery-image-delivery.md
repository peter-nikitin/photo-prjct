# Выпуск CDN изображений и архивов

Схемы доставки описаны в [ADR 0069](../adr/0069-serve-media-through-cdn-without-imgproxy.md) и
[ADR 0071](../adr/0071-prepare-photo-archives-in-background.md).
Маршрутизация, группы источников и HTTPS управляются Terraform через
[Infrastructure по ADR 0073](../adr/0073-manage-media-cdn-with-terraform.md).

## Инфраструктурный выпуск

1. Проверить сохранённый план в PR. Для первоначального переноса ожидаются только
   импорты действующих ресурсов. Для первого выпуска ZIP ожидается создание одного
   правила `module.media_cdn.findmecdn_rule.private_archives`.
2. Подтвердить конкретный запуск `/infra approve <run-id>`. После слияния Infrastructure
   применяет этот план. При создании ZIP провайдер читает действующий ключ подписи
   правила превью. При изменении существующих правил он сохраняет используемые секреты.
3. Проверить успешный apply, HTTPS на `img.findme-photo.ru` и выдачу существующих фото.
   До включения флага архивов проверить закрытый бакет и суточный lifecycle префикса `archives/`.

Если меняется исходный код провайдера, пересобрать пакеты Go на `darwin_arm64` и
`linux_amd64` командой `infra/ci/install-cdn-provider.sh <каталог>`. Для второй
платформы задать `GOOS` и `GOARCH`. Обновить запись провайдера в lock-файле командой
`terraform providers lock -fs-mirror=<каталог>/mirror -platform=darwin_arm64 -platform=linux_amd64 terraform.findme-photo.ru/findme/findmecdn`
из `infra/terraform`. Локальный Terraform использует `TF_CLI_CONFIG_FILE=<каталог>/terraform.rc`.

Для первичной установки ключей задать `TF_VAR_cdn_secure_key` и
`TF_VAR_cdn_origin_auth` из закрытой проекции Lockbox при планировании и применении.
Terraform передаёт значения только на запись. При согласованной ротации существующего
правила задать новую несекретную `credentials_revision`, чтобы план содержал обновление.

## Проверка и включение

1. В режиме `staff` взять URL обложки, обычного и водяного превью, оригинала для просмотра
   и оригинала для скачивания. Использовать тестовые фотографии.
2. Запросить непрогретое превью. Ответ `200` и правильный файл подтверждают, что SigV4 дошёл до
   S3. Выпустить новую подпись на тот же путь и убедиться, что CDN отдаёт `HIT`. Для
   закрытых превью и оригиналов проверить отказ без подписи и с просроченной подписью даже на
   прогретом кеше. Запросить неподдерживаемый путь и убедиться, что он не обслуживается.
3. Проверить отказ на маршруте Django без секретного заголовка. Для платного фото проверить
   отказ без покупки, затем имя файла при скачивании с правом доступа. Проверить отдельно
   `Range` при холодном и прогретом запросе, включая `206`, `Content-Range` и байты ответа.
4. Включить флаги в `on` и сравнить `GET` в Object Storage при сопоставимом трафике галерей.
   Проверить долю `HIT`, ошибки источников и сетевую нагрузку ВМ на промахах по оригиналам.

В разделе **CDN и Object Storage** дашборда FindMe Photo видны запросы, доля `HIT`,
ответы `304`, трафик, доля `5xx` и p95 времени скачивания с CDN. Для бакетов доставки и
оригиналов показаны `GET` и `HEAD` по бакетам. Доля ответов CDN вне кеша считается по
статусам `MISS`, `EXPIRED` и `NO_CACHE` среди всех статусов кеша CDN.
Например, 20% соответствует 200 ответам вне кеша на 1000 запросов.
`NO_CACHE` включает ответы без кеширования, в том числе отказы в доступе.
Метрики бакетов включают обращения Django и других потребителей, поэтому фоновые чтения
учитываются при оценке нагрузки на S3.

При провале проверки или откате установить оба флага в `off`. Новые запросы снова используют
обычную выдачу. Для приватных ссылок, выданных ранее, доступ ограничен сроком подписи.
Не записывать подписанные URL и значения секретного заголовка в логи выпуска.

## Выдача ссылок без HEAD

`PrivateUploadStorage.sign_final` и `CdnFinalObjectStorage.sign_final` подписывают точный
final key локально, без `HEAD` или чтения S3. Это убирает ожидание ответа Object Storage
из `photo_media` и `photo_download`: при диагностике web ожидание `HeadObject` увеличивало
среднее время ответа до 87–95 секунд. Срок подписи, имя скачиваемого файла и локальная
валидация ключа сохраняются.

Перед подписью приложение по-прежнему проверяет видимость мероприятия, принадлежность
фотографии, готовность принятого превью и право на оригинал. Для платной выдачи остаются
проверки оплаченного заказа и доступа покупателя; административная выдача сохраняет
свою проверку доступа. Подпись выдаёт право получить конкретный объект, но не подтверждает
его существование в момент выдачи. Если объект удалён вне приложения, отсутствие
обнаружится при получении файла из S3 или при промахе кеша CDN; прогретая копия может
оставаться доступной до истечения срока кеша. Проверки объектов при приёме и обработке
медиа, чтении потока и обращении CDN к источнику сохраняются.

Изменение выпускается штатным Deploy для web после слияния PR, без миграций и изменений
инфраструктуры. До и после выпуска сравнить задержки и `504` на `photo_media` и
`photo_download`, проверить выдачу разрешённого файла и отказ без прав. При регрессии
откатить web штатным Deploy.

## Браузерный кеш

CDN задаёт годовой `max-age` публичным обложкам. При замене обложки приложение создаёт
новый ключ и видимый URL. Приватные превью и оригиналы получают `private, no-cache`.
Браузер может сохранить копию и отправить `If-None-Match` при повторном запросе на ту же
подписанную ссылку. CDN проверяет подпись и может ответить `304`. Выпуск новой подписи
меняет URL для браузера. Срок хранения на CDN определяется отдельной настройкой.

После изменения правил проверьте `Cache-Control` у каждого типа изображения, `304` на
прогретой подписанной ссылке с подходящим `ETag` и отказ на прогретой копии при
просроченной подписи. Для проверки `ETag` оригинала выберите файл, который CDN ещё не
закешировал со старыми заголовками.


## Проверка ZIP-архивов

`archive-worker` сохраняет два параллельных слота и единоличное владение через advisory lock.
Каждый слот подписывается на PostgreSQL `archive_jobs` до первой проверки очереди. Приём,
явный повтор неудавшегося архива и восстановление прерванного задания посылают пустое
уведомление в транзакции изменения задания. Пустая очередь ожидает сигнал без SQL-опроса;
после сигнала слоты продолжают захват через `SKIP LOCKED` до опустошения. Если захват
пропустил видимые queued строки под блокировкой другого запроса, слот повторяет попытку
через полсекунды или раньше по уведомлению. Это сохраняет обработку при откате дубликата,
который снимает блокировку без нового сигнала. Действительно пустая очередь таймера захвата
не имеет. При разрыве
соединения слот переподписывается и повторяет чтение таблицы. При SIGTERM ожидание прекращается
не позднее локальной секундной проверки остановки; текущие сборки завершаются до освобождения
advisory lock. Периодическая очистка архивов остаётся у главного потока.
Телеметрия использует отдельный канал и не участвует в пробуждении слотов.


1. Включить `bulk-photo-download` для staff и подготовить тестовый архив размером более
   10 МБ. Повторить для бесплатной выдачи и оплаченного заказа. Отдельно проверить, что
   запрос без права доступа к исходной странице не создаёт задание.
2. Выполнить подписанный `GET` через CDN. Проверить `200`, корректный ZIP, имя файла в
   `Content-Disposition` и `Cache-Control: private, no-store`. Для проверки заголовков
   сохранить их из ответа на `GET`, поскольку подпись запроса привязана к HTTP-методу.
3. Получить новую подпись того же архива, повторить `GET` и проверить `Cache-Status: HIT`
   с прежним `Content-Disposition`. Проверить `Range` на холодном и на прогретом кеше.
   Ожидаются `206`, корректный `Content-Range` и запрошенные байты. Правило
   `private-archives` кеширует ответы `200` и `206` на 600 секунд и включает загрузку
   крупных объектов сегментами. Подпись URL не входит в ключ кеша.
   Для заголовков источника используется штатная политика CDN. API отклоняет параметр
   `cacheHttpHeaders` при создании правила.
4. Проверить отказ без токена и с токеном по истечении срока, в том числе после прогрева
   кеша. Убедиться, что приложение отправляет браузер на адрес CDN.
   Отдельно проверить, что соседний ключ под `uploads/` недоступен через CDN.
5. После проверки включить `bulk-photo-download`. При откате перевести флаг в `off`. Если нужно прекратить выдачу по действующим ссылкам,
   удалить правило ZIP следующим согласованным планом Terraform.
   Ранее выданные ссылки CDN сохраняют доступ до истечения подписи. Подписанные URL и
   содержимое архивов не должны попадать в логи выпуска.

Параметры правила и поведение токенов описаны в документации Yandex Cloud.
[Параметры правила](https://yandex.cloud/en/docs/cdn/api-ref/ResourceRules/create),
[кеширование](https://yandex.cloud/en/docs/cdn/concepts/caching),
