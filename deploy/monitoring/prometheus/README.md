# Дашборд и критические алерты

Этот каталог нужен разработчику, который меняет графики, правила или код их публикации в Yandex
Monitoring. Устройство сбора и хранения метрик описано в
[архитектуре](../../../docs/architecture.md#observability), подтверждённый статус — в
[инженерном реестре](../../../docs/engineering-jobs.md#ej-009--operator--detect-service-degradation).

## Текущие точки входа

- `single-vm-dashboard.json` — графики Linux, Django, PostgreSQL и Web Vitals для одной VM,
  а также размер очередей и длительности этапов поиска по селфи и фото галереи.
- `single_vm_dashboard.py` — проверка конфигурации и обновление существующего дашборда
  независимо от свежести метрик. Совпадающий дашборд не перезаписывается.
- `rules.yml` — единственный набор критических правил; `rules.test.yml` проверяет их поведение.
- `alertmanager.yml` — маршрутизация в существующие email и Telegram с восстановлением.
- `alerts.py` — публикация правил после проверки источников, резервная копия и read-back.
- `verify_metrics.py` — проверка свежих серий VM, приложения или коллектора очередей.
- `environment.json` — идентификаторы каталога, workspace и дашборда.
- `oidc.json` — настройки доступа workflow через GitHub OIDC.
- `control.py` — используемые скриптом функции доступа к API и проверки данных.
- `requirements.txt` — отдельные зависимости инструментов мониторинга; они не входят
  в зависимости Django и обработчиков.

## Как доставляются изменения

[Workflow Monitoring](../../../.github/workflows/monitoring.yml) проверяет изменения в PR:
структуру дашборда через SDK, синтаксис и сценарии алертов через `promtool`. После merge изменения
дашборда применяются автоматически независимо от выпуска источников. Изменения правил
применяются после появления свежих исходных серий, отдельно от обновления дашборда. Infrastructure проверяет
метрики VM после настройки ОС, Deploy проверяет Django и PostgreSQL после выпуска приложения
или exporter. Сбой проверки виден в соответствующем выпуске. Резервная копия
изменяемого дашборда сохраняется в артефактах workflow.

Сборщики находятся отдельно: конфигурация Unified Agent — в
[роли Ansible](../../../infra/ansible/roles/monitoring/), PostgreSQL exporter — в
[Compose](../../../docker-compose.deployment.yml) и
[его каталоге](../../postgres-monitoring/).

Для повторной проверки выберите scope `vm` или `application` в Actions → **Verify metrics**.
Проверка читает сырые выборки через Prometheus Remote Read, без изменения облачных ресурсов.

Внешний probe описан в [Terraform](../../../infra/terraform/public_probe.tf). Его сборка
находится в [deploy/public-probe](../../public-probe/), read-only наблюдение очередей — в Django.
Архив probe загружается в одном артефакте с одобренным plan и используется при apply без
пересборки. Конфигурация Alertmanager имеет документированный PUT, но её API read-back
не подтверждён: фактическую маршрутизацию и доставку проверяют в UI и контролируемым сигналом.

## Телеметрия очередей

После коммита готового результата исполнитель в отдельной транзакции вызывает `pg_notify`
с лимитом SQL 100 мс. Ошибка этой транзакции оставляет готовый результат доступным
пользователю. Во время отправки исполнитель ждёт ответа PostgreSQL. Для каждого готового
поиска с полным набором времён отправляется одно событие на канал `queue_telemetry`.

Пример события:

```json
{
  "event": "queue.task.completed",
  "version": 1,
  "queue": "gallery_search",
  "segments_ms": {"matching_wait": 5000, "matching_elapsed": 15000}
}
```

Исполнитель задаёт имена очереди и этапов в коде. `gallery_search` передаёт `matching_wait`
и `matching_elapsed`. `selfie_search` дополнительно передаёт `recognition_wait` и
`recognition_elapsed`. Ожидание заканчивается на первом запуске соответствующего этапа.
Распознавание заканчивается постановкой в SQL-очередь, а поиск — публикацией результата.
Повторы после первого запуска входят во время этапа. Если отметка времени отсутствует или
нарушен порядок этапов, событие пропускается. Разности округлённых смещений от
постановки сохраняют сумму этапов в целых миллисекундах.

Коллектор принимает до 32 очередей и до 16 этапов на очередь. Имена соответствуют
`[a-z][a-z0-9_]{0,31}`, тело ASCII JSON занимает до 2048 байт. Длительность этапа
принимается целым числом от 0 до 2 147 483 647 мс. Первое принятое событие
фиксирует состав этапов для своей очереди до перезапуска. Чтобы изменить состав с
сохранением интерпретации истории, используйте новую метку очереди. Поля с идентификаторами
или данными задачи не входят в протокол.

`queue-telemetry` использует одно постоянное соединение с PostgreSQL. После обрыва сервис
переподписывается. Уведомления, отправленные без активного подписчика, могут теряться.
Счётчики в памяти сбрасываются при перезапуске коллектора, а первая выборка новой серии
задаёт начальную точку для расчёта прироста. При опросе HTTP коллектор читает согласованный
снимок в памяти без обращения к БД. Глубина очередей и p75 времени до готовности за 24 часа
по-прежнему рассчитываются Django из PostgreSQL.

### Выпуск и проверка

1. Infrastructure применяет конфигурацию Unified Agent из роли Ansible. Агент опрашивает
   `http://127.0.0.1:9188/metrics` раз в минуту под job `findme-queue-telemetry`.
2. Deploy запускает коллектор из того же `APP_IMAGE` после основных сервисов. Ошибка
   запуска видна по `QUEUE_TELEMETRY_START=failed` в журнале Deploy. Дашборд выпускается
   отдельным workflow Monitoring. Между этими шагами графики длительностей могут быть пустыми.
3. На VM проверьте `curl -fsS http://127.0.0.1:9188/metrics`. Затем из каталога репозитория
   запустите `deploy/monitoring/prometheus/verify_metrics.py queue-telemetry` с помощью Python
   окружения с зависимостями из этого каталога и действующей авторизацией `yc`.
   Проверка требует свежую серию `findme_queue_telemetry_listening` со значением 1 в Prometheus.
   Для проверки самих счётчиков завершите по одному успешному поиску обоих видов, дождитесь
   опроса агента и проверьте `findme_queue_completed_total` и
   `findme_queue_segment_duration_seconds_total` с нужными метками.

При откате к ревизии до коллектора сначала выполните на VM из `/opt/photo-prjct`
`docker compose --project-name photo-prjct --env-file .env -f docker-compose.deployment.yml rm -sf queue-telemetry`,
пока сервис есть в Compose. Затем выпустите предыдущие версии приложения, конфигурации
Unified Agent и дашборда. Восстановление БД не требуется.

### Запросы для новой очереди

В запросах ниже замените `gallery_search` на метку новой очереди. Имена этапов берутся
из метки `segment`. Время этапа в секундах на одну успешную задачу для графика с накоплением:

```promql
sum by (segment) (rate(
  findme_queue_segment_duration_seconds_total{job="findme-queue-telemetry",queue="gallery_search"}[5m]
))
/ on () group_left() (sum(rate(
  findme_queue_completed_total{job="findme-queue-telemetry",queue="gallery_search"}[5m]
)) > 0)
```

Для кругового графика используйте суммарное время по этапам за пять минут до конца
выбранного периода. Выберите представление `PIE` и агрегацию `LAST`.

```promql
sum by (segment) (increase(
  findme_queue_segment_duration_seconds_total{job="findme-queue-telemetry",queue="gallery_search"}[5m] @ end()
))
```

## Web Vitals

После выпуска приложения запись `web-vitals` появляется в Django Admin со статусом `off`.
Установите `staff` для проверки под активной учётной записью сотрудника на основном HTTPS-домене.
После проверки выберите `on`, чтобы подключить сбор для посетителей.

Публичные страницы в графиках — каталог (`catalog`), страница мероприятия (`gallery`),
документы (`legal`), вход фотографа (`photographer_login`), корзина (`cart`) и список
«Мои заказы» (`orders`). При сопоставлении с Django смотрите маршруты `event_catalog`,
`event_detail`, `legal`, `photographer_login`, `commerce:detail` и `commerce:order_list`
соответственно. Доступ к корзине и списку заказов определяется флагами покупки.

1. После первого опроса Unified Agent отметьте текущие значения исходных счётчиков
   `findme_web_vitals_lcp_seconds_count{job="findme-http"}`,
   `findme_web_vitals_inp_seconds_count{job="findme-http"}`,
   `findme_web_vitals_ttfb_seconds_count{job="findme-http"}` и
   `findme_web_vitals_cls_count{job="findme-http"}`.
2. В режиме `staff` откройте галерею опубликованного мероприятия. Каталог сотрудника
   подключает скрипт, только если не показывает черновики. В DevTools → Network включите
   сохранение журнала, дождитесь отрисовки, взаимодействуйте со страницей и переключитесь на
   другую вкладку. Проверьте `POST /telemetry/web-vitals/` с ответом 204. В запросе должны
   отсутствовать `Cookie` и `Referer`, в теле ожидаются только тип страницы, класс ширины окна
   и доступные замеры. INP появляется при измеренном взаимодействии. Повторное скрытие той же
   вкладки не дублирует ранее отправленный замер. На следующем опросе проверьте рост счётчиков
   для соответствующего типа страницы и класса ширины окна.
3. В группе **Web Vitals** проверьте оценку p75 и число наблюдений за скользящие 24 часа.
   Сравнивайте одинаковые типы страниц и классы ширины окна. Для каждой метрики объём выборки
   свой, а значения при малом числе замеров могут заметно меняться от визита к визиту.
   В первом ряду сравните браузерный TTFB с p75 времени Django для тех же маршрутов.
   TTFB включает сеть, а серверный график показывает все успешные GET без разбивки по ширине окна.
4. После перехода в `on` повторите проверку без входа в аккаунт на публичных страницах.

Чтобы выключить сбор, установите `off` в Django Admin. Откройте каталог заново и убедитесь,
что скрипт не подключается. Приёмник продолжает принимать корректные пакеты, в том числе из уже
открытых вкладок. Исторические замеры остаются на дашборде, пока доступны в Prometheus.
