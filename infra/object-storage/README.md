# Параметры бакетов приложения

[ADR 0068](../../docs/adr/0068-separate-originals-event-media-and-operational-storage.md)
определяет три независимых роли. Приложение после переключения получает имена из переменных
`ORIGINALS_S3_BUCKET`, `OPERATIONAL_S3_BUCKET` и `EVENT_MEDIA_S3_BUCKET`.
Deploy image origin использует то же `EVENT_MEDIA_S3_BUCKET`.

Схема имени `findme-photo-media-<роль>-<окружение>-<суффикс>`. Роли по порядку таблицы
`originals`, `scratch` и `delivery`. Для рабочего окружения используем `prod`, а конкретный
суффикс выбираем при подготовке бакетов с учётом доступности глобальных имён.

| Бакет | Настройка и права |
| --- | --- |
| Оригиналы | Приватный. Учётная запись приватных медиа читает и публикует объекты `originals/`. У операций отката загрузки есть право удалить свой неподтверждённый объект. Deploy записывает новые оригиналы в `COLD`. |
| Временные файлы | Приватный `STANDARD` без версионирования. Учётная запись приватных медиа работает с `uploads/`, `preview-jobs/` и `selfie-search/`. CORS для загрузок находится здесь. [Конфигурация S3 lifecycle](operational-lifecycle.json) задаёт два правила. Каждый процесс удаляет созданные им временные файлы. Lifecycle страхует очистку превью и селфи. Срок для брошенных загрузок определяется состоянием партии. |
| Медиа мероприятий | `STANDARD`, общие флаги анонимного доступа выключены. Учётная запись приватных медиа публикует и читает `previews/`. У image origin есть отдельное право чтения этого префикса. Учётная запись обложек пишет только в `event-covers/`. При сохранении обложке назначается объектный ACL `public-read`. |

[Правило записи обложек](event-cover-writer-policy-statement.json) и [правило image origin](image-origin-policy-statement.json)
добавляются в общую политику бакета с сохранением остальных согласованных правил.
При выключенном публичном доступе Yandex Cloud проверяет объектный ACL для анонимных запросов.
Публичный ACL назначается только обложкам. Превью и оригиналы должны быть недоступны
при анонимном чтении без подписанной ссылки.
[Порядок проверки доступа](https://yandex.cloud/ru/docs/storage/security/overview).
Lifecycle JSON описывает состояние нового временного бакета. Конфигурацию существующего бакета
сверяют целиком перед заменой.

Перед переключением проверяются наличие данных по ключам PostgreSQL, запрос CORS от реального
origin, публикация оригинала с ожидаемым классом, стандартный класс превью, выдача обложки без
токена, отказ для превью без токена и доступ с токеном, а также правила очистки временных файлов.
При инвентаризации постоянных объектов нужно учесть исторические ссылки `Photo.src`, если они
ещё используются. Порядок переноса данных и переключения рассматривается отдельно.

## Порядок выпуска

1. Подготовить три новых бакета и выдать права существующим учётным записям по таблице.
   Оставить действующие переменные Deploy привязанными к текущим бакетам. На этом этапе
   можно проверить CORS, lifecycle, `CopyObject` между бакетами, чтение с подписью и публичный
   ACL обложек на отдельных контрольных объектах.
2. Перенести постоянные объекты и сверить ключи с PostgreSQL. При копировании готовых
   превью заменить префикс `derivatives/previews/` на `previews/`. В окне переключения
   обновить сохранённые ссылки на эти ключи и включить восстановление прежних ссылок в откат. Перед финальной сверкой
   остановить записи по старой схеме. Незавершённые загрузки, задачи обработки и поиск по селфи
   завершить или разобрать по отдельному плану переключения.
3. Заполнить новые переменные бакетов и выпустить приложение и image origin с новой схемой.
   Проверить галерею, обложки, скачивание, загрузку и поиск. На время проверки сохранить старые
   бакеты и комплект предыдущей конфигурации для отката.
4. После приёмки и окончания окна отката удалить прежние бакеты и старые переменные
   отдельной операцией.

Слияние инфраструктурного PR публикует параметры в Git. Подготовка облачных ресурсов проходит
отдельной операцией после определения имён, учётных записей и проверки прав в рабочем каталоге.
