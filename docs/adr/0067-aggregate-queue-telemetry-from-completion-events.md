# 0067: Собирать телеметрию очередей из событий завершения

- Status: Accepted
- Дата: 2026-11-14
- Авторы решения: владелец проекта
- Заменяет: нет
- Заменено: нет

## Контекст

Оператору нужно видеть, какие этапы занимают время фоновых задач и как меняются их доли.
Поиск по селфи и по фото галереи использует разные наборы этапов и общий исполнитель
сопоставления. Расчёт накопленных длительностей из всей истории при каждом опросе метрик
растёт вместе с объёмом данных.

## Мотивы

- Собирать одинаковые метрики для очередей с разным жизненным циклом.
- Ограничить стоимость сбора независимо от глубины истории.
- Сохранять результаты задач при сбоях телеметрии и ограничивать задержку отправки.
- Подключать очереди без изменения коллектора и без общего движка исполнения.

## Рассмотренные варианты

1. Читать новые завершения из PostgreSQL с перекрытием по времени и дедупликацией.
   Это изолирует воркеры от публикации, но требует учитывать границы чтения и поздние коммиты.
2. Хранить счётчики в каждом процессе исполнителя и опрашивать эти процессы напрямую.
   Прямой сбор дёшев, если число целей опроса и их адреса известны.
3. Передавать компактные события через PostgreSQL `LISTEN/NOTIFY` и агрегировать их
   в отдельном процессе. События доступны активным подписчикам и теряются при отключении.
4. Использовать transactional outbox с доставкой из отдельного процесса. Он позволяет
   восстанавливать поток после сбоя ценой записи события в рабочей транзакции и обслуживания журнала.

## Решение

Используем PostgreSQL `LISTEN/NOTIFY` для телеметрии завершений. Владелец очереди определяет
границы этапов и после коммита успешного результата отправляет компактное версионированное
событие с типом очереди и длительностями этапов. Длительности одного события составляют
полное измеренное время без перекрытия. Имена меток задаёт код издателя, персональные
данные и идентификаторы задач в событие не входят.

Отдельный коллектор читает канал через одно соединение, проверяет формат, ограничивает
число меток и накапливает в памяти число завершений и сумму секунд по этапам. Новые
очереди подключаются через тот же формат. Unified Agent опрашивает готовые счётчики,
а Prometheus хранит их историю. База сохраняет состояние задач независимо от доставки
телеметрии. Ошибка отправки после коммита оставляет готовый результат доступным.

Доли считаются из приростов секунд за одно окно. Для каждой точки графика делим прирост
по этапу на общий прирост по очереди. Круговая диаграмма показывает тот же состав у конца
выбранного периода. График средних в секундах помогает отличить рост доли от роста самой
длительности. При отсутствии измеренных завершений или нулевом суммарном времени доли
отсутствуют. Длительность окна задаётся запросами дашборда.

## Последствия

- Стоимость опроса определяется числом серий. Коллектор не перечитывает историю задач.
- Отправка уведомления добавляет короткий SQL-вызов после завершения. Перезапуск коллектора
  сбрасывает счётчики, а отключение подписчика оставляет пропуски в данных. Метрики
  описывают наблюдаемую выборку и подходят для диагностики скорости.
- Состояние очереди и время уже завершившихся задач измеряются отдельно. Доли по
  завершениям не показывают возраст задач, которые ещё ждут.
- Если потребуется использовать каждое завершение для работы продукта или восстанавливать
  пропущенные события, нужно пересмотреть гарантии доставки.

## Проверка и откат

Проверяем доставку после коммита, отсутствие события при откате, сохранение результата
при ошибке отправки и восстановление подписки после разрыва. Проверка PromQL подтверждает
изменение долей, сумму 100% при наличии времени и разрыв без завершений. После выпуска
сверяем поступление серий в Prometheus. Откат затрагивает коллектор, приложение,
конфигурацию агента и дашборд. Схема и данные очередей остаются доступны.
