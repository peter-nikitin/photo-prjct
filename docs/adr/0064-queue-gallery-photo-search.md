# 0064: Выполнять поиск по фотографии галереи через очередь PostgreSQL

- Status: Accepted
- Date: 2026-11-09
- Deciders: владелец проекта; согласовал спецификацию и явно предоставил все разрешения и согласования для реализации 2026-11-09
- Supersedes: [ADR 0024](0024-use-gallery-face-as-search-query.md) только в части браузерного process POST, выполнения поиска в HTTP-worker и отсутствия фонового задания
- Superseded by: none

## Контекст

После выбора лица в галерее Django создаёт queued-поиск, но вычисление запускает POST
из вкладки результата. Точное SQL-ранжирование и расширение результата занимают HTTP-worker
и способны задерживать другие страницы. Работа должна продолжаться после закрытия браузера.
PostgreSQL уже хранит состояния, векторы и результаты; размещение ограничено одной VM.

## Мотивы

- Освобождать HTTP-worker сразу после долговременного приёма запроса.
- Сохранить точный поиск, права доступа и неизменяемый bearer-результат.
- Обрабатывать задания без зависимости от открытой вкладки и восстанавливаться после сбоя.
- Использовать существующие Django/PostgreSQL без дополнительного брокера или VM.

## Рассмотренные варианты

1. Очередь PostgreSQL и отдельный процесс приложения Django с доступом к БД.
2. Celery с Redis/RabbitMQ: дополнительный брокер и согласование доставки со state в БД.
3. Существующий ML-worker через API: запуск через callback оставляет SQL-вычисление в HTTP-worker,
   а полный перенос требует другого протокола данных или полномочий.

## Решение

Выбран вариант 1. Gallery-origin SelfieSearch в queued — долговременная единица работы.
Запись запроса и его постановка в очередь происходят одним коммитом. Один процесс Django
последовательно забирает работу и атомарно публикует существующее ранжирование и ready.
Проверки processing, конфигурации и текущего источника сохраняются.

В текущем Compose управляется один исполнитель. При каждом старте он до первого claim возвращает все gallery-origin processing в queued, обнуляет их
счётчик попыток и сразу разрешает выполнение. Это прямое решение владельца проекта:
старый процесс остановлен до нового; файловой блокировки и lease нет. Другие состояния,
selfie jobs и готовые результаты не сбрасываются. При недоступной БД startup recovery
повторяется с ограниченным backoff до первого claim.

SIGTERM завершает процесс немедленно, без drain. При выпуске worker останавливается с
нулевым timeout до миграции. Web проходит свою проверку готовности, затем запускается
исполнитель без ожидания queue health. Отдельного health command или heartbeat нет.
Живая попытка ограничена watchdog 150s; ранжирование имеет scoped SQL-бюджет 120s,
остальные SQL — 30s, lock — 1s и connect — 5s; временная ошибка живого
исполнителя допускает до трёх попыток с задержкой 5s. После рестарта processing всегда
восстанавливается независимо от прежнего счётчика и задержки. Ошибка БД после старта,
при которой retry не удаётся сохранить, завершает процесс для обычного Docker restart.

Публичные HTTP-запросы не выполняют поиск. Статус только читает сохранённое состояние и
счётчики, без обхода галереи или выдачи media URL; размер ответа не зависит от размера мероприятия.
Клиент использует polling и загружает существующую страницу результата после завершения.
Process endpoint и его браузерные повторы удаляются, синхронного fallback нет.

Новый исполнитель — процесс приложения, как Commerce, с доступом Django к PostgreSQL.
Это не photo-worker: его прежняя граница закрытого API без DB credentials сохраняется.
Загрузка селфи и её ML-пайплайн не меняются. Выбранное лицо, модель, пороги, изоляция мероприятия,
приватность query-вектора, авторизация медиа и семантика сохранённого результата не меняются.

## Последствия

Появляется отдельный управляемый процесс и ограниченная логика claim, startup reset, retry
и timeout. HTTP-worker освобождается от вычислений, но конкуренция за общие ресурсы VM и
БД остаётся: доступность страниц под реальной нагрузкой проверяется отдельно. Новые платные
ресурсы не разрешены. Несколько исполнителей и rolling overlap не поддерживаются;
изменение такой топологии потребует отдельного решения.

## Проверка и восстановление

Проверить работу без браузера, короткие HTTP-запросы во время поиска, read-only статус,
немедленное завершение subprocess по SIGTERM и повторный startup, fresh/exhausted processing,
сохранность queued/ready/failed/selfie и атомарность готового снимка. Live retry сохраняет
предел трёх попыток; startup обнуляет его только у восстановленных processing.

При выпуске остановить старый worker немедленно и старый web, применить схему, дождаться
готовности web и запустить один исполнитель. При сбое остановить приём новых запросов и
исправить выпуск; принятые задания и результаты сохраняются. Возврат к старому синхронному
process endpoint не является поддерживаемым откатом. Lease, lock и health infrastructure
не добавляются для гипотетической второй копии.
