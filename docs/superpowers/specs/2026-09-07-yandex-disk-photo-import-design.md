## Результат и границы

Фотограф открывает существующую страницу загрузки, выбирает мероприятие и его папку,
вставляет публичную ссылку Яндекс Диска и нажимает **«Загрузить»**. Сервер сохраняет задачу,
самостоятельно переносит JPEG-оригиналы в наше приватное S3-совместимое Object Storage и
подключает каждое подтверждённое фото к стандартному циклу обработки.

После подтверждения приёма задачи вкладку можно закрыть. Исходники на Яндекс Диске не
изменяются и не удаляются: «перенос» означает копирование. После успешного импорта наша
копия самостоятельна и не зависит от доступности ссылки.

В первый вариант входят публичная папка без пароля и OAuth, только её прямые файлы,
сохраняемый прогресс, повтор после ошибок и пропуск уже импортированного содержимого.
ZIP, другие облака, приватные папки, синхронизация по расписанию, рекурсивный обход,
воссоздание каталогов и изменение уже опубликованных оригиналов не входят в этот вариант.

## Сценарий на странице загрузки

1. Пользователь выбирает мероприятие через существующий интерфейс.
2. Для нужной существующей папки выбирает загрузку по ссылке Яндекс Диска. Поддерживается
   также **«Без папки»**. Создание папок остаётся в существующем управлении мероприятием.
3. Вводит одну ссылку на публичную папку. Одно нажатие создаёт один импорт для одной
   пары «ссылка — папка мероприятия». Для другой папки или ссылки запускает следующий импорт.
4. Нажимает **«Загрузить»**. Сервер проверяет формат ссылки, права и принадлежность папки,
   фиксирует владельца, мероприятие, папку и источник в PostgreSQL и возвращает идентификатор
   задачи. До этого ответа интерфейс не обещает, что импорт принят.
5. Появляется карточка задачи с сообщением **«Задача принята. Можно закрыть страницу —
   загрузка продолжится на сервере»**. Проверка доступности ссылки и перечисление файлов
   выполняются в фоне, а не внутри запроса создания задачи.
6. После перечисления карточка показывает число JPEG, подпапок и неподдерживаемых файлов.
   Все найденные прямые подпапки пропускаются. При их наличии показывается предупреждение:

   > В папке по ссылке есть вложенные папки. Фотографии из них загружены не будут.

   Предупреждение не блокирует импорт и сохраняется при возвращении на страницу. Рядом с
   полем ссылки заранее указано: **«Загрузим только JPEG-файлы из указанной папки, без подпапок»**.
7. Каждое успешно импортированное фото начинает стандартную обработку сразу после
   подтверждения оригинала, без ожидания остальных файлов.

Страница показывает принадлежащие пользователю задачи, включая завершённые, с ограниченной
постраничной выдачей. Возвращение на страницу восстанавливает серверный прогресс без повторного
ввода ссылки. Локальная загрузка файлов сохраняет собственную существующую очередь;
её ограничения открытой вкладки не распространяются на серверный импорт.

## Файлы и состав импорта

- Принимается ссылка `https://disk.yandex.ru/d/<ключ>` или публичная ссылка `https://yadi.sk/d/<ключ>`.
  Ссылка должна непосредственно обозначать нужную опубликованную папку. Произвольные URL,
  внутренние адреса, страницы личного Диска и ссылка на одиночный файл отклоняются.
- Обходим постранично только непосредственное содержимое этой папки. Для записей `type=dir`
  учитываем предупреждение, но не запрашиваем их содержимое и download URL.
- Кандидаты — прямые файлы с расширением `.jpg`/`.jpeg` без учёта регистра. Остальные файлы
  пропускаются с отдельным счётчиком. Реальное содержимое каждого кандидата проверяется как JPEG;
  расширение и MIME не заменяют проверку байтов.
- Размер одного JPEG — не более **52 428 800 байт (50 МиБ)**, как у существующей загрузки.
  Превышение даёт ошибку файла и не мешает остальным допустимым файлам.
- Для ограниченного перечисления первый вариант допускает не более **10 000 прямых записей**
  в исходной папке, включая подпапки и неподдерживаемые файлы. Превышение отклоняет импорт
  целиком до переноса байтов; пользователь получает просьбу разделить исходную папку.
- Перед передачей первого файла завершается перечисление и фиксируется манифест: источник,
  путь, имя, размер, тип, доступные хэши и метаданные версии. Повтор страницы перечисления
  не создаёт второй item для того же пути.
- Это зафиксированный результат обхода, а не обещание атомарного снимка Яндекс Диска.
  API не даёт оснований обещать такой снимок при одновременном изменении папки. Интерфейс просит
  не менять её содержимое до завершения проверки; обнаруженное противоречие страниц прерывает
  проверку с предложением повторить импорт. Файлы, добавленные после завершения обхода,
  попадут только в следующий новый импорт.
- Если JPEG нет, задача завершается без создания `Photo` с сообщением
  **«В указанной папке нет JPEG-файлов для загрузки»** и найденными предупреждениями.

## Повторная загрузка и идентичность

Повтор той же публичной папки тем же пользователем в ту же папку того же мероприятия
пропускает уже успешно импортированное содержимое. Область сравнения: владелец импорта,
канонический ключ исходной папки, мероприятие и папка назначения, включая `Без папки`.
Это ограниченный контракт данного способа загрузки, а не глобальная дедупликация медиабанка.

Идентичность содержимого определяется SHA-256 и точным размером. Первый успешный импорт
сохраняет вычисленный по полученным байтам SHA-256 и связь с подтверждённой `Photo`.
Если API сообщает SHA-256, его можно сравнить с уже проверенным содержимым до скачивания.
Если SHA-256 в ответе отсутствует, файл скачивается и хэшируется до решения о публикации;
имя, размер, MD5 или Object Storage ETag по отдельности не являются основанием для пропуска.
Такая проверка может потребовать повторной передачи байтов из Диска, но не создаёт дубликат в S3.

- Совпадение имени при другом содержимом создаёт новое фото; старое фото не заменяется.
- Переименование файла с тем же содержимым в той же исходной папке не создаёт новое фото.
- Несколько одинаковых файлов внутри одного импорта дают одно новое фото и пропуски остальных.
- Ошибочные и незавершённые элементы не считаются успешно импортированными.
- Другая папка назначения или другое мероприятие разрешают отдельный импорт того же фото.
- Фотографии из локальной загрузки, других исходных папок или импорта другого пользователя
  не участвуют в сравнении. Их наличие и служебные метаданные не раскрываются через импорт.
- Повтор HTTP-запроса после потери ответа с тем же ключом отправки возвращает ту же задачу.
  Два одновременных импорта в одной области сравнения не публикуют два фото с одинаковым хэшем:
  решение о пропуске и публикации сериализуется на сервере.
- Если все подходящие файлы уже импортированы, результат — **«Новых фотографий нет»**,
  а не ошибка. Повторно ставить обработку для пропущенных фото нельзя.

## Компоненты и поток данных

Выбран отдельный фоновый import-worker с задачами в PostgreSQL и закрытым Django API,
по образцу принятой модели взаимодействия processing worker. Он относится к ingestion:
его работа начинается до существования `Photo`. В первом варианте — один исполнитель,
одна передача файла одновременно, без внешнего брокера.

`ImportBatch` концептуально хранит владельца, источник, неизменяемое назначение, состояние
перечисления, манифест и итог. `ImportItem` хранит идентичность источника, попытки,
проверенный хэш и результат: подтверждённое фото, пропуск либо ошибку. Названия здесь
обозначают доменные сущности, а не предписывают полный набор таблиц и полей миграции.

1. Django принимает задачу и владеет состояниями, авторизацией, lease, retries и публикацией.
2. Import-worker получает ограниченную по времени аренду через закрытый API и перечисляет
   источник через публичный Disk API; страницы манифеста сохраняются через Django.
3. Для очередного файла worker получает свежий download URL, скачивает в ограниченный
   временный файл, проверяет размер, доступные хэши источника и JPEG, вычисляет SHA-256.
4. Django проверяет возможность пропуска. Для нового содержимого выдаёт краткоживущий grant
   только на созданный сервером приватный incoming key текущей попытки.
5. Worker отправляет байты прямо в Object Storage. Django проверяет идентичность incoming
   объекта и публикует immutable original через общий контракт подтверждения ingestion.
6. В авторитетной операции создаются `Photo`, связь с импортом и задания обычной обработки.
   Назначаются исходный пользователь, мероприятие и выбранная папка. Текущие правила
   `policy_for_new_photo`, метаданных, preview и последующей обработки применяются так же,
   как при локальной загрузке. Время съёмки не подменяется временем импорта или изменения на Диске.
7. Успех сохраняется до получения worker ответа. Потеря ответа, рестарт или повтор
   подтверждения возвращают уже достигнутый результат, не создавая вторую `Photo`.

Общий контракт публикации должен использоваться обоими способами загрузки без копирования
правил обработки. Закрытый worker API не выдаёт worker сессию фотографа и не открывает
пользовательские endpoints для произвольной подмены владельца.

Байты не проходят через обычный пользовательский Django/Gunicorn запрос. При размещении
import-worker на текущей VM они всё равно занимают сеть и временный диск этой VM; это
не storage-to-storage copy и не обещание бесплатной либо мгновенной передачи.
Worker не получает постоянные S3-ключи, доступ к PostgreSQL или Django secret.

## Контракт Яндекс Диска

Основание: [официальные операции над опубликованными файлами и папками](https://yandex.ru/dev/disk-api/doc/ru/reference/public),
проверено 2026-09-07. Это контракт интеграции; скорость и фактические ограничения источника
должны подтверждаться на реальной папке при реализации.

| Операция | Контракт |
| --- | --- |
| Содержимое папки | `GET https://cloud-api.yandex.net/v1/disk/public/resources`, `public_key`, `limit`, `offset`, стабильная сортировка по имени |
| Выбор файлов | Только прямые `_embedded.items`; пагинация до конца списка, без рекурсивных запросов |
| Получение ссылки файла | `GET https://cloud-api.yandex.net/v1/disk/public/resources/download`, `public_key` исходной папки и точный `path` элемента |
| Авторизация | Для публичного источника OAuth и cookies пользователя не нужны |
| Передача | Полученный `href`, проверенный `method=GET`, без шаблонизации; новый URL перед каждой попыткой |

Ключи и пути кодируются HTTP-клиентом как query-параметры. Ручное склеивание URL и разбор
пользовательской HTML-страницы не используются. Download endpoint вызывается для отдельного
JPEG, а не для папки целиком. Поля SHA-256 и версии сохраняются, когда доступны; их наличие
не предполагается обязательным по примеру документации. Доступные хэши источника проверяются
по загруженным байтам; несоответствие размера или хэша манифесту означает изменение источника
и ошибку данного файла. Новое содержимое можно принять новым импортом.

`href` не хранится как постоянный источник и не возвращается браузеру. Обращение к нему
происходит только после проверки HTTPS, допустимого download-host и отсутствия userinfo.
Редиректы проверяются на каждом переходе; соединения к loopback, private, link-local,
metadata и другим непубличным адресам запрещены, включая DNS rebinding. Разрешённые
download-hosts подтверждаются по официальному API и реальному интеграционному примеру;
неизвестный адрес отклоняется, а не разрешается как произвольная внешняя загрузка.

## Прогресс, ошибки и восстановление

Пользовательские стадии: **«В очереди»**, **«Проверяем папку»**, **«Загружаем»**,
**«Приостановлено»**, **«Завершено»**, **«Завершено с ошибками»**, **«Не удалось загрузить»**.
Внутренние счётчики основаны на сохранённых items. Карточка показывает мероприятие, папку,
время запуска, импортированные, уже имеющиеся, ошибочные и ожидающие файлы, а также
предупреждения. Список файлов и ошибок имеет ограниченную постраничную выдачу.

Завершение импорта означает сохранение оригиналов и постановку предусмотренных текущей
конфигурацией задач обработки. Оно не означает готовность всех превью или лиц. Интерфейс
сообщает: **«Загрузка завершена. Обработка фотографий продолжается»**, если обработка ещё идёт;
её прогресс берётся из существующего processing состояния, не из счётчика скачиваний.

| Ситуация | Наблюдаемое поведение |
| --- | --- |
| Ошибка формата или назначения | Запрос не создаёт задачу; понятная ошибка возле поля |
| Ссылка недоступна, закрыта, указывает на файл | Фоновая проверка завершает задачу с понятной причиной, без импорта |
| В папке есть подпапки / не-JPEG | Предупреждение / счётчик пропущенного; допустимые JPEG продолжают загружаться |
| Пустая папка / только дубли | Нормальный итог без новых `Photo` |
| JPEG слишком большой, повреждён, изменён или удалён | Ошибка конкретного файла; остальные продолжаются |
| Timeout, `429`, `5xx`, истёкший download URL или S3 grant | Ограниченные автоматические retries с backoff, jitter, учётом `Retry-After` и свежим grant/URL |
| Повторные временные сбои | Не более четырёх попыток одной операции за цикл, затем видимая ошибка; нет бесконечного активного retry |
| Worker завершился / потерял связь | После истечения lease задача снова доступна; серверный прогресс сохраняется |
| Сбой после копирования в final или создания `Photo` | Восстановление завершает ту же публикацию; immutable original не заменяется |
| Ошибка последующей обработки | Фото остаётся импортированным; ошибка и повтор принадлежат стандартному processing |

Одна передача после обрыва начинается заново; частичное скачивание файла не возобновляется.
Кнопка **«Повторить ошибки»** повторяет только ошибочные элементы сохранённого манифеста,
с новым ограниченным бюджетом попыток, не пересканирует папку и не трогает успешные элементы.
После ошибки самого перечисления она повторяет перечисление с начала до передачи файлов.
Для добавленных или изменённых файлов пользователь запускает новый импорт по ссылке.

## Доступ, хранение и включение

Сохраняется `ingestion.upload_photos`: staff сам по себе не даёт права загрузки. Пользователь
выбирает мероприятие по текущим правилам, но читает и повторяет только собственные импорты;
superuser имеет административный доступ. Папка обязательно принадлежит мероприятию,
назначение фиксируется при создании. Ссылка на папку назначения защищена от удаления,
переименование не меняет назначения.

Публичный ключ исходника хранится только в закрытом состоянии импорта. Ссылки, signed URL,
токены и внешние тела ошибок не попадают в обычные логи, аналитику, публичную галерею и
клиентские ответы прогресса. Имена файлов выводятся как экранированный текст. Приватные
оригиналы и производные подчиняются существующим правилам публикации и платного доступа.

Временный файл worker удаляется после попытки; прерванные временные файлы очищаются при
восстановлении. Неиспользуемые incoming/final objects следуют существующей границе очистки
после 24 часов без активности. Очистка не удаляет объект действующей попытки или
подтверждённое фото. Подтверждённые оригиналы не получают новый срок автоматического удаления.
Состояние импорта и проверенные отпечатки сохраняются для повторов; отдельный lifecycle
удаления истории в этот вариант не входит.

Новая функция доставляется под кодовым gate `yandex-disk-import`, изначально `off`, с
обычным управлением `off` / `staff` / `on` в Django Admin по ADR 0028/0032. Gate не заменяет
права загрузки. Создание, повтор, claim следующей работы и публикация проверяют текущую
доступность функции для владельца задачи и его актуальные права. При закрытии gate или
отзыве прав работа приостанавливается без потери прогресса; уже начавшаяся передача может
дойти до incoming, но не обходит проверку публикации. После восстановления доступа
продолжается с сохранённого состояния. Чтение собственного прогресса остаётся доступным
при выключенном gate при наличии права загрузки.

Регистрация gate принадлежит web startup; worker её не выполняет. Этот документ не
разрешает миграции, изменение инфраструктуры, включение worker или gate на действующем сервисе.

## Выбор подхода и архитектурное согласование

Выбран отдельный исполнитель ingestion с PostgreSQL/Django-контролем: он поддерживает
задачи до создания фото и освобождает браузер, сохраняя принятые границы worker credentials.
Повторное использование `ProcessingJob` для ещё не существующей `Photo` смешало бы импорт
и обработку. Скачивание в пользовательском web-запросе не обеспечивает независимость
от запроса и длительно занимает web-процесс. Новый брокер не нужен для данного объёма задачи.

Принятый ADR 0035 разрешает новый путь: ADR 0014 прямо исключал ingestion worker, а ADR 0013
выбирал передачу исходников мимо VM. Здесь вводится дополнительный серверный путь и его
сетевая нагрузка. ADR 0017 служит образцом протокола, но сам по себе не утверждает импорт.
ADR 0035 отдельно принят пользователем; ADR 0013/0014 получили узкие ссылки на supersession.
`docs/architecture.md` описывает импорт как принятое, но ещё не реализованное решение.

## Критерии приёмки

1. Авторизованный пользователь выполняет заявленный сценарий для папки или `Без папки`;
   после ответа о принятии закрывает браузер, а оригиналы и обычная обработка появляются в фоне.
2. Импорт получает все прямые JPEG из многостраничного ответа. Подпапки не перечисляются
   рекурсивно, не скачиваются; предупреждение видно и после повторного открытия страницы.
3. Чужая или удалённая папка назначения отклоняется; успешные `Photo` сохраняют владельца,
   мероприятие и назначение, включая переименование папки во время импорта.
4. Повтор той же ссылки пропускает проверенное содержимое в согласованной области;
   одинаковое имя с другими байтами создаёт новое фото. Проверяются переименование,
   отсутствие SHA-256 у источника, параллельные повторы и отсутствие повторных processing jobs.
5. Перезапуск worker и потеря ответа после публикации не теряют прогресс и не создают дублей.
   Просроченный worker не может опубликовать результат чужой или завершённой попытки.
6. Повреждённый, изменённый или слишком большой JPEG не мешает остальным; временные ошибки
   ограниченно повторяются. Повтор ошибок не трогает успешные items и не добавляет новые пути.
7. Пустая папка, только подпапки, только дубли и превышение лимита дают описанные итоги,
   без ложного сообщения о новых фото. Незавершённая проверка не запускает передачу.
8. Состояние импорта не выдаётся за готовность обработки. Бесплатные и платные мероприятия
   используют те же правила публикации и processing, что локальная загрузка.
9. Права, ownership, gate, приватные адреса, редиректы и редактирование источника проверяются
   на соответствующих границах. Worker не имеет постоянных storage/database credentials.
10. На реальном публичном JPEG подтверждена цепочка Disk API → private incoming → immutable
    original → `Photo` → стандартная обработка, включая фактический download-host и редиректы.
    Проверка не утверждает производительность для 10 000 файлов без отдельного измерения.
11. Страница остаётся пригодной для большого списка на мобильном и desktop: ограниченная
    выдача, доступные с клавиатуры поле и кнопка, видимое предупреждение, ошибки и итог.
