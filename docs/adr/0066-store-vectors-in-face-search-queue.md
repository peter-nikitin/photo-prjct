# 0066: Передавать вектор в задаче общей очереди поиска по лицу

- Status: Accepted
- Дата: 2026-11-12
- Авторы решения: владелец проекта
- Заменяет: [ADR 0019](0019-use-public-event-selfie-search.md) в части ранжирования внутри
  callback и запрета временного сохранения вектора запроса,
  [ADR 0025](0025-expand-selfie-search-with-face-clusters.md) и
  [ADR 0040](0040-use-pgvector-for-exact-face-search.md) в части этого запрета,
  [ADR 0064](0064-queue-gallery-photo-search.md) в части ограничения очереди источником из
  галереи и получения вектора исполнителем по ссылке на лицо.
- Заменено: нет

## Контекст

Распознавание загруженного селфи и SQL-поиск по лицу занимают разные ресурсы. Для распознавания
уже есть очередь ML-воркеров, а для поиска по фотографии галереи — фоновый исполнитель с очередью
PostgreSQL. В обоих сценариях вектор уже доступен в момент постановки задачи поиска.

## Мотивы

- Фиксировать приём вектора и постановку поиска одной транзакцией PostgreSQL.
- Освобождать ML-воркер сразу после постановки задачи поиска.
- Использовать один формат задач и один исполнитель SQL-поиска для селфи и галереи.
- Ограничить доступ к вектору селфи и срок его использования.

## Рассмотренные варианты

1. Хранить вектор в самой задаче поиска в PostgreSQL и удалять завершённые задачи по расписанию.
2. Передавать вектор исполнителю через память процесса. После сбоя вектор потребуется получить
   заново, а очередь теряет возможность продолжить уже принятый поиск с тем же входом.

## Решение

Выбран вариант 1. SQL-поиск по лицу использует одну очередь PostgreSQL, один формат задачи
и один фоновый обработчик. Задачи поступают в неё из двух мест:

- **Callback воркера распознавания селфи.** Закрытый HTTP-обработчик проверяет полномочия
  попытки, валидирует вектор и берёт ID мероприятия из связанного запроса поиска. Одной
  транзакцией он принимает результат распознавания и записывает вектор прямо в задачу поиска
  в PostgreSQL. Успешный ответ отправляется после коммита. Повтор callback подтверждает
  уже принятую попытку, а устаревший callback не меняет её результат. Действующая очередь
  ML-воркеров обслуживает этап получения вектора селфи.
- **Запуск поиска по фото галереи.** Django проверяет доступность исходной фотографии для
  пользователя и пригодность выбранного лица, читает его готовый вектор из PostgreSQL и ставит
  задачу сразу в общую очередь.

Сущность «Поиск» хранит текущий этап обработки. Поиск по селфи начинается с этапа
«Распознавание» и переходит в этап «Поиск совпадений» в той же транзакции, которая ставит
задачу SQL-поиска. Поиск по фото галереи сразу начинается с этапа «Поиск совпадений».
Ожидание и повторы сохраняют текущий этап. После завершения применяется итоговый статус
самого поиска.

Страница результата показывает одно сообщение «Ищем фотографии…» для всего времени
ожидания результата. Оно используется при первой загрузке и при обновлении статуса через
polling. Внутренний этап и нахождение задачи в очереди в интерфейсе скрыты. Готовый результат
и итоговая ошибка отображаются по итоговому статусу поиска.

Каждая задача содержит ID поиска, ID мероприятия и вектор с идентификатором модели. Метка
источника используется только для статистики. Постановка после получения вектора, выбор
готовых задач, ранжирование pgvector, повторы и публикация используют общий путь. Итоговый статус поиска и завершение задачи сохраняются в одной транзакции. Изменения доступности исходной фотографии после постановки задачи
не отменяют поиск и не мешают публикации. При показе результата Django проверяет актуальную
доступность найденных фотографий. Если среди совпадений есть исходная фотография, к ней
применяется та же проверка при показе.

Векторы хранятся в отдельной таблице очереди. Очистка по cron удаляет завершённые задачи с векторами
после успеха или окончательной ошибки, включая задачу, которую исполнитель завершил по истечении
срока. Задачи в работе и задачи, ожидающие
повтора, остаются в очереди. Результат поиска, времена этапов для статистики и сведения для
подтверждения повторного callback сохраняются независимо от строки очереди.

Для селфи сохраняется предел использования вектора в 24 часа с момента постановки на
распознавание, без продления при повторе или перезапуске. По истечении срока исполнитель
завершает задачу с ошибкой. Исполнитель SQL-поиска публикует результат при сохранении в PostgreSQL. Временное селфи
остаётся в закрытом хранилище до удаления отдельной командой на стороне web. Запись поиска
сохраняет ключ до подтверждения удаления. Сбой хранилища оставляет снимок на повторную очистку.
Это решение заменяет условие ADR 0019 об удалении до публикации.

Логические выгрузки и клоны исключают данные таблицы очереди. После восстановления такой копии
задачи без входа завершаются с ошибкой, а сохранённые результаты доступны. Физические копии
PostgreSQL в Cloud Backup могут содержать векторы селфи до истечения срока хранения копий
по действующей политике. Владелец проекта согласовал это 2026-11-13.
Векторы задач исключены из логов, метрик и публичных ответов.

## Последствия

- Для передачи вектора воркер распознавания использует существующий закрытый callback.
- Перезапуск фонового исполнителя сохраняет принятый вход и не требует повторного распознавания.
  Потеря базы и восстановление логической копии имеют другую семантику: временный вход
  в копии отсутствует.
- Постановка задачи по фото галереи временно дублирует её вектор. Оба источника делят общий
  лимит выполнения SQL-поисков.

## Проверка и пересмотр

Проверить отсутствие ранжирования в callback, атомарность приёма и постановки, повторную
доставку, одинаковое выполнение задач независимо от метки источника и восстановление после
перезапуска. Для селфи проверить атомарный переход между этапами, для галереи — старт с поиска
совпадений. При первой загрузке и при polling один и тот же текст должен отображаться на обоих
этапах и в ожидании повтора. Проверить, что очистка удаляет только завершённые строки,
а после неё результат доступен, повторный callback не создаёт задачу и статистика сохраняется.
Логическая копия не содержит данных очереди. Поиск должен завершаться, если исходную фотографию скрыли
после постановки. Скрытое совпадение должно исчезать из выдачи при следующем показе.
В метриках размера и времени по этапам различать селфи и галерею. Для селфи отдельно измерять
ожидание распознавания и ожидание поиска.
