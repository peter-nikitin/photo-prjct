# Архитектура FindMe Photo

## Назначение документа

Этот документ описывает устройство системы и её границы. **Реализовано** означает наличие
работающего пути в коде, **принято** — решение в [ADR](adr/README.md), **активировано** —
подтверждённое состояние конкретного развертывания. Эти состояния не подменяют друг друга.
Датированные свидетельства реализации и эксплуатации находятся в
[продуктовом](product-jobs.md) и [инженерном](engineering-jobs.md) реестрах и в
[операционных документах](operations.md). Текст удалённых спецификаций и планов доступен в
истории Git, но не определяет действующие правила.

## Цель продукта

FindMe Photo помогает участникам массовых мероприятий находить фотографии по номеру, лицу и
данным события, а фотографам и операторам — загружать, проверять и публиковать снимки.
Покупка даёт доступ к выбранным закрытым оригиналам. Все виды поиска ограничены мероприятием;
результат распознавания означает вероятное совпадение, а ручная правка имеет приоритет над
машинным кандидатом.

<a id="current-architecture--implemented"></a>
## Реализованная система

```text
Браузер → Nginx/HTTPS → Django/Gunicorn → PostgreSQL
                           │
                           ├→ закрытые оригиналы и производные в Object Storage
                           ├→ приватный API обработки → пулы photo-worker
                           └→ платёжный шлюз и доставка писем через Commerce worker

GitHub Actions → GHCR → каноническая VM и пулы worker
```

Django 6 — модульный монолит. Он владеет правилами продукта, авторизацией, HTTP-интерфейсом и
транзакционным состоянием. PostgreSQL — источник истины для событий, фотографий, заданий,
результатов обработки, поисковых снимков, корзин и заказов. Object Storage хранит байты
оригиналов и производных. Обработчики работают отдельно и обращаются к Django через закрытый
аутентифицированный API; они не получают прямой доступ к базе и постоянные ключи Object Storage.
Основы определены [ADR 0001](adr/0001-django-modular-monolith.md),
[0002](adr/0002-postgresql-system-of-record.md),
[0003](adr/0003-docker-compose-yandex-cloud.md) и
[0017](adr/0017-use-django-polled-photo-processing-jobs.md).

Один канонический сервис обслуживает `https://findme-photo.ru/`. Приложение выпускается через
Docker Compose, общий Nginx/Certbot edge и workflow **Deploy**. Образы web и photo-worker могут
выпускаться независимо; изменение только документов не требует выпуска образа. Worker capacity
вынесена в отдельные пулы и отдельный cloud folder, но база и полномочия выпуска остаются
каноническими. Настройку и фактическое состояние нужно проверять по
[runbook развёртывания](runbooks/deployment.md) и
[runbook пулов](runbooks/worker-pools.md), а не выводить из наличия кода. См.
[ADR 0028](adr/0028-operate-one-canonical-deployment.md),
[0042](adr/0042-isolate-autoscaled-photo-worker-pools.md),
[0046](adr/0046-isolate-worker-pool-management-in-a-separate-folder.md) и
[0051](adr/0051-release-photo-worker-images-independently.md).

<a id="accepted-constraints"></a>
## Принятые границы

- Секреты не хранятся в Git. Утверждённая версия секрета находится в Yandex Lockbox; workflow
  получает её через ограниченные полномочия, а процессы приложения читают только выданные им
  значения окружения. Локальные `.env` остаются вне Git.
- Для пользовательских функций с незавершёнными условиями запуска используются явные runtime
  gates. Наличие модели, обработчика или маршрута не означает публичную активацию.
- Приватные оригиналы не становятся публичными ключами Object Storage. Подписанная выдача
  конкретного объекта следует после проверки полномочий и имеет ограниченный срок.
- Каталог, поиск, обработка и покупка сохраняют отдельные границы полномочий. Выбор фото в
  корзине не создаёт права скачать оригинал.
- Наблюдение и оповещения опираются на измеренные признаки влияния на сервис; отсутствие
  телеметрии не считается нулевой нагрузкой. Настройка правила и фактическая доставка
  уведомления требуют разных доказательств.

<a id="deployment-domain-assignment--accepted"></a>
## Домен и выпуск

Канонический адрес — `https://findme-photo.ru/`; HTTP и `www` перенаправляются на него. Для
изменения имени, сертификата или границы доступности требуется отдельное операционное решение.
Публичный probe выполняется независимо от VM приложения на image-origin VM. Workflow применяет
изменения приложения и наблюдаемости по составу затронутых компонентов. Успешный CI или Deploy
сам по себе не доказывает состояние DNS, TLS, runtime gates, данных или пользовательского пути.
Подробности: [ADR 0011](adr/0011-use-minimal-shared-https-rollout.md),
[0039](adr/0039-run-public-probe-on-image-origin-vm.md) и
[0053](adr/0053-reconcile-observability-independently-on-main.md).

<a id="target-mvp-architecture--proposed"></a>
## Модули и ответственность

| Модуль | Ответственность |
| --- | --- |
| Каталог | `Event`, публикация, публичные страницы и выбор мероприятия. |
| Загрузка | Права фотографа, партии, локальная загрузка и импорт с Яндекс Диска. |
| Медиа | Закрытые оригиналы, принятые производные, правила галереи и точная подписанная выдача. |
| Обработка | Долговременные задания, аренды, попытки, проверка результатов и версии моделей. |
| Поиск | Номер участника, селфи, лицо из галереи, фильтры мероприятия и сохранённые результаты. |
| Commerce | Корзины, заказы, подтверждение оплаты, права на оригиналы и доставка доступа. |
| Операции | Развёртывание, секреты, метрики, оповещения, диагностика и восстановление. |

Это логические границы. Они не требуют отдельного сервиса для каждого модуля. Извлечение
самостоятельных сервисов возможно только при подтверждённой потребности.

<a id="photo-ingestion-and-indexing"></a>
## Загрузка и обработка фотографий

Фотограф с отдельным разрешением создаёт партию для мероприятия. Браузер отправляет оригиналы
прямо в закрытый входящий префикс Object Storage по краткоживущему разрешению. Django проверяет
загруженный объект, связывает подтверждение с его ETag и переводит его в закрытый постоянный
ключ. Папка мероприятия — метаданные каталога, а не префикс хранилища и не источник доступа.
Состояние партии и элементов сохраняется в PostgreSQL, поэтому незавершённую загрузку можно
возобновить без повторного подтверждения готовых элементов. Импорт с Яндекс Диска имеет
самостоятельные долговременные попытки и выключен по умолчанию. См.
[ADR 0012](adr/0012-use-django-photographer-permissions.md),
[0013](adr/0013-use-direct-private-object-storage-ingestion.md),
[0014](adr/0014-keep-stage-2-ingestion-request-driven.md) и
[0035](adr/0035-use-django-polled-yandex-disk-import.md).

После подтверждения Django ставит версионированные задания. PostgreSQL хранит состояние,
аренду, повторы и неизменяемые попытки. Worker получает краткоживущие разрешения только на
конкретные входные и выходные объекты. Принятие результата и публикация производной происходят
транзакционно. Для новой ветки обработки сначала создаётся проверенный preview, затем на его
основе запускается распознавание лица. Генерации процессоров и моделей не смешиваются; ошибка
не подменяется успешным результатом. Отдельные bulk и selfie worker обслуживают соответствующие
очереди. Изменение контракта worker требует проверки существующего состояния, отложенных заданий,
производных и порядка отката.

<a id="search"></a>
## Поиск

Публичная галерея сначала ограничивается опубликованным мероприятием и доступными фотографиями.
Папка, время и номер участника только сужают этот набор. Номер ищется точным сравнением строки
`BibReading` в пределах события; начальные нули значимы. Результаты распознавания и ручные правки
имеют раздельную историю, а в поиск попадают только текущие принятые номера.

Запрос по лицу создаётся из загруженного селфи или явно выбранного лица на фотографии галереи.
Селфи временно обрабатывается worker и удаляется до публикации результата; в базе не сохраняется
вектор запроса. Второй путь использует уже принятое лицо и сразу создаёт результат без временного
изображения. Сравнение выполняется точно в PostgreSQL через pgvector по совместимой когорте
AdaFace `vector(512)` в рамках одного события. Отсутствующее или несовместимое свидетельство
отклоняется; численно пограничные результаты обрабатываются по
[ADR 0041](adr/0041-accept-pgvector-numerical-boundaries.md).

Результат — неизменяемый снимок вероятных совпадений с bearer-ссылкой. Он не утверждает личность
человека и не расширяет доступ к обычной платной галерее. Дополнительное расширение по
консервативным кластерам лиц независимо включается отдельным gate и не меняет прямые результаты.
См. [ADR 0019](adr/0019-use-public-event-selfie-search.md),
[0024](adr/0024-use-gallery-face-as-search-query.md),
[0025](adr/0025-expand-selfie-search-with-face-clusters.md),
[0040](adr/0040-use-pgvector-for-exact-face-search.md) и
[0054](adr/0054-retire-sface-and-fix-adaface-vector-dimension.md).

<a id="purchase-and-download"></a>
## Покупка и выдача оригиналов

Платная галерея показывает только принятую производную с водяным знаком для новой платной
генерации. Оригинал остаётся закрытым. Анонимная корзина хранится на сервере отдельно для
каждого мероприятия и даёт только право выбора. При оформлении состав и цена фиксируются в
неизменяемом заказе. Право на каждый оригинал выводится из позиции **оплаченного** заказа;
возврат браузера с платёжной формы не является доказательством оплаты. Подтверждение приходит
из проверенного шлюза или от уполномоченного администратора. Доступ к заказу открывает
отдельный отзывный ключ, уведомление по email доставляется асинхронно.

Реализация Commerce содержит адаптер Т-Банка, обработку уведомлений, сверку неопределённых
попыток, Yandex Postbox и отдельный worker. Публичный запуск зависит от банковской песочницы,
фискальных настроек, юридической проверки, явного gate и наблюдаемого результата; локальные
тесты не подтверждают выполнение этих условий. Потоковый ZIP ограничен одной страницей
авторизованных оригиналов и отдельным gate. См.
[ADR 0029](adr/0029-use-watermarked-previews-for-paid-photos.md),
[0030](adr/0030-use-anonymous-server-side-event-carts.md),
[0031](adr/0031-use-orders-and-adapters-for-paid-original-delivery.md),
[0034](adr/0034-stream-page-scoped-photo-archives-through-django.md) и
[0047](adr/0047-separate-order-payment-from-new-cart-selection.md).

<a id="security-privacy-and-legal-boundaries"></a>
## Безопасность, персональные данные и право

- Оригиналы и биометрические данные ограничены мероприятием и конкретным контекстом доступа.
  Публичная выдача не раскрывает постоянный ключ объекта или ключи хранилища.
- Лицо даёт вероятное совпадение, не установление личности. Именная идентификация, поиск между
  мероприятиями и расширенное повторное использование биометрии требуют нового решения.
- Селфи удаляется до публикации результата. Согласованная обратная связь по качеству хранится
  отдельно, с ограниченным доступом и сроком жизни; она не разрешает обучение модели.
- Скрытие фотографии обратимо и прекращает новую публичную выдачу, но не отменяет уже оплаченное
  право, завершённую передачу или ранее выданный краткоживущий URL.
- Платёжные уведомления аутентифицируются и обрабатываются идемпотентно. Право на скачивание
  выводится из состояния заказа в PostgreSQL.
- Доступ сотрудников к закрытым медиа, ручные правки и разрешение коммерческих исключений
  требуют отдельной проверки полномочий и аудита.
- Лицензии моделей, библиотек, наборов данных и внешних API проверяются для коммерческого
  применения. Резервное копирование и восстановление данных сервиса требуют отдельного
  подтверждённого операционного контракта.

<a id="evolution-stages"></a>
## Развитие системы

Развитие идёт от работающего каталога и загрузки через повторяемую обработку и поиск к
публичной покупке и подтверждённой эксплуатационной готовности. Состояние каждого шага
указывается в реестрах задач; целевая возможность не считается реализованной или активной
только потому, что она описана здесь или принята в ADR.

<a id="checkout-payment-entitlement-and-original-delivery-seam"></a>
### Граница оформления и оплаты

Корзина выбирает фотографии; заказ фиксирует их и цену; платёжное свидетельство переводит заказ
в оплаченный статус; позиция оплаченного заказа даёт право на оригинал. Выдача медиа остаётся
отдельной проверкой `PublicMediaResolver`. Письмо сообщает доступ, но не создаёт его.

<a id="open-decisions"></a>
## Открытые решения

Отдельного решения и доказательств требуют: целевые RPO/RTO и проверка восстановления;
возвраты платежей и их влияние на доступ; более широкое управление биометрическими данными;
порог перехода от опроса PostgreSQL к иной очереди; необходимость приблизительного векторного
индекса; дальнейшее развитие распознавания номеров. Отсутствие решения не следует заполнять
предположением в плане реализации.

<a id="change-rules"></a>
## Правила изменения архитектуры

Долговременный выбор, его альтернативы и причины фиксируются в новом ADR. Принятое решение
изменяется новым ADR со взаимными ссылками; история прежнего текста сохраняется. Фактически
реализованную границу обновляют в этом документе и подтверждают кодом или операционным
свидетельством. Временные спецификации и планы удаляются из индекса Git до слияния PR по
[ADR 0055](adr/0055-keep-accepted-decisions-not-working-documents.md).
