## Контекст

Прежние VM после инцидента считаются утраченными. Сначала требуется вернуть доступность
сайта без нагрузки. Восстановление прежних размеров и количества ресурсов воспроизведёт
расходы, необходимость которых для текущего состояния проекта не подтверждена.
Нужна минимально жизнеспособная конфигурация работающего сервиса с дальнейшим ростом
по фактической потребности.

## Мотивы

- Минимизировать постоянные расходы при работающем обязательном наборе функций.
- Не оплачивать запас под гипотетическую нагрузку и не наследовать прежние размеры.
- Учитывать весь состав платных ресурсов, включая диски и сетевые сервисы.
- Сохранять данные и продуктовые границы доступа при сокращении ресурсов.

## Варианты

1. Восстановить прежний состав и размеры ресурсов как исходный запас мощности.
2. Заранее выделить мощности под предполагаемую будущую нагрузку.
3. Начать с минимальной конфигурации, проверить обязательные функции и увеличивать
   ресурсы только по измеренной необходимости.

## Решение

Выбрать вариант 3. Критерий выбора — минимальные затраты на конфигурацию, которая
подтверждённо выполняет текущие обязательные функции. Доступность сайта восстанавливается
первой; обработка проверяется следующим этапом на тех же ресурсах. Пока обработчики
не прошли проверку, восстановление всех функций не объявляется завершённым.

Начальная реализация этого принципа — одна VM для PostgreSQL, Django, последовательного
photo-worker, import, Commerce и image origin. Начальный размер — минимум выбранной
платформы: 2 vCPU, 20%, 1 ГБ RAM. Диски выбираются по измеренному объёму БД, образов
и рабочих файлов, без запаса «на рост». Instance Groups, autoscaler и отдельный
worker-folder не восстанавливаются.

На минимальном хосте не резервируется память для второго web-slot или одновременно
прогретой замены worker. Допустим перерыв при обновлении; требование непрерывного
обслуживания потребовало бы отдельно обосновать дополнительные ресурсы.

Увеличение размера или добавление ресурса требует конкретного ограничения, измерений
и рассмотренной стоимости изменения. Автоматического масштабирования нет. Одна VM —
выбранная текущая конфигурация; дальнейшее размещение определяется тем же критерием
работоспособности и затрат. Отдельно принятые требования, например постоянный вход NLB,
входят в исходные ограничения и общий расчёт расходов.

PostgreSQL использует самостоятельный диск данных, который не удаляется при замене VM.
Photo-worker обращается к закрытому API Django с токеном, без прямого доступа к БД
и постоянных S3-ключей. Image origin сохраняет отдельные ограниченные права на производные.
Соседство контейнеров не меняет авторизацию медиа и контракты ADR 0050/0054.

## Последствия

Проект начинает с небольших постоянных расходов и растёт по фактической потребности.
Сокращение ресурсов требует измерений и может ограничивать скорость обработки.
Общий отказ единственной VM останавливает весь сервис; допустим downtime.
ML-обработка может не поместиться на начальном размере: это фиксируется как конкретное
ограничение, а увеличение ресурсов рассматривается явно. БД, медиа и права покупателей
сохраняются независимо от оптимизации затрат.

## Проверка

Зафиксировать состав ресурсов и оценку постоянных и переменных расходов; для каждого
ресурса должно быть понятно, какую текущую потребность он покрывает. Проверить публичный
сайт, сохранение БД при повторном deploy, изоляцию контейнерных прав и реальные
последовательные processing/import/Commerce операции. Решение об увеличении ресурсов
сопровождается измеренной причиной и изменением стоимости.
