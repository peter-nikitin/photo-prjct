# Архитектура FindMe Photo

## Назначение документа

Это краткая схема текущей системы и её границ. **Реализовано** означает рабочий путь в коде,
**принято** — решение в [ADR](adr/README.md), **активировано** — подтверждённое состояние
конкретного развертывания. Статус функций и свидетельства работы находятся в
[продуктовом](product-jobs.md) и [инженерном](engineering-jobs.md) реестрах. Причины и условия
архитектурных решений раскрыты в ADR; процедуры — в [операционных документах](operations.md).

## Задача системы

FindMe Photo помогает участникам мероприятий находить снимки по номеру, лицу и данным события,
а фотографам и операторам — загружать и публиковать фотографии. Поиск ограничен мероприятием;
совпадение лица вероятностное, а ручная правка имеет приоритет. Доступ к закрытому оригиналу
зависит от правил галереи и подтверждённой покупки.

<a id="current-architecture--implemented"></a>
## Текущая схема кода

```text
GitHub Actions Infrastructure → Terraform (VPC, диски, одна VM)
                              → Ansible (пользователь, SSH, Docker, PG mount)
                              → подготовленная ОС
GitHub Actions Deploy → immutable образы → Compose (db, web, edge, обработчики)
```

Django — модульный монолит: он владеет HTTP-интерфейсом, полномочиями и правилами продукта.
PostgreSQL — источник истины для состояний и результатов. Object Storage хранит байты медиа.
Обработчики запускаются рядом с Django и обращаются к нему по внутренней Docker-сети. Основу закрепляют
[ADR 0001](adr/0001-django-modular-monolith.md),
[0002](adr/0002-postgresql-system-of-record.md),
[0003](adr/0003-docker-compose-yandex-cloud.md) и
[0017](adr/0017-use-django-polled-photo-processing-jobs.md).

<a id="deployment-domain-assignment--accepted"></a>
## Инфраструктура и развёртывание

Желаемое состояние инфраструктуры и ОС хранится в Git: код служит единым источником истины,
по которому окружение можно воспроизвести и проверить. Изменения проходят общий процесс
PR → merge → release. Этот принцип закреплён в [ADR 0057](adr/0057-declarative-cloud-infrastructure.md)
и [ADR 0063](adr/0063-repeatable-host-configuration.md).

Ответственность разделена по слоям:

- **Terraform** описывает облачные ресурсы: сети, VM, диски и публичный вход. Provider связывает
  конфигурацию с API облака; state учитывает созданные ресурсы и хранится вне VM.
- **Ansible** описывает конфигурацию ОС: пользователей, SSH, пакеты, Docker, mounts и системные
  службы. Один способ настройки применяется и к новой VM, и при дальнейшем обслуживании хоста.
- **Docker Compose и Deploy** отвечают за выпуск контейнеров приложения и обработчиков.
  Настройка ОС и выпуск приложения имеют отдельные границы ответственности.

GitHub Actions связывает эти слои в общий release. В PR проверяются конфигурация, Terraform plan
и оценка стоимости; изменения ресурсов согласуются до merge. После merge автоматически
применяется одобренный plan, затем необходимые изменения ОС и приложения. Для изменения
только одного слоя выполняются соответствующие шаги. Фактический результат проверяется
пайплайном; ошибка применения означает неуспешный release.

Размещение следует принципу минимально жизнеспособной конфигурации: одна VM для PostgreSQL,
Django и обработчиков, отдельный сохраняемый диск БД и Object Storage для медиа. Мощности
увеличиваются по измеренной потребности ([ADR 0056](adr/0056-minimum-viable-infrastructure.md)).
Порядок выпуска описан в [инструкции выпуска](runbooks/deployment.md).

Для независимого от VM публичного адреса используется постоянный IP NLB с TCP forwarding;
TLS завершается на Nginx/Certbot ([ADR 0058](adr/0058-stable-public-entrypoint-nlb.md)).
Nginx направляет запросы по Host к Django или image origin по приватной сети. При переносе
сервиса меняется его приватный upstream, при переносе edge — цель NLB; публичный адрес и DNS
сохраняются. SSH использует отдельный служебный доступ к VM. Секреты и SSH-доступ описаны
в [отдельном разделе](#secrets-and-ssh-access).

<a id="observability"></a>
## Наблюдаемость (observability)

Метрики охватывают ресурсы VM, HTTP-запросы Django, доступность БД из приложения и состояние
PostgreSQL. Сбор, хранение и визуализация разделены:

```text
Linux ────────────────────┐
Django /metrics/ ─────────┼→ Unified Agent → Remote Write → управляемый Prometheus → дашборд
PostgreSQL → exporter ────┘
```

- **Хранение метрик вынесено из VM.** Управляемый Prometheus сохраняет историю независимо от
  замены хоста и не требует содержать локальную базу временных рядов на минимальной VM.
  Unified Agent работает как системная служба: собирает метрики Linux напрямую и опрашивает
  Django и PostgreSQL exporter. Локальный дисковый буфер сглаживает временную недоступность
  приёмника; сбор ограничен по частоте и ресурсам, чтобы не вытеснять приложение.
- **Метрики не публикуются в интернете.** HTTP-точки Django и exporter доступны агенту через
  loopback, а публичный Nginx закрывает `/metrics/`. Exporter использует отдельную роль БД
  с `pg_monitor`, без superuser и полномочий изменять прикладные данные. Его пароль поступает
  из Lockbox отдельно от пароля приложения. Для Remote Write агент получает IAM-токен через
  metadata service account VM; постоянный ключ облака на хосте не нужен.
- **Конфигурация наблюдаемости хранится в Git и выпускается по слоям.** Terraform задаёт IAM,
  Ansible устанавливает и настраивает агент, Compose описывает exporter. В Deploy настройка
  exporter выполняется отдельной job после успешного выпуска приложения: её сбой виден
  отдельно и не меняет результат уже завершённой job приложения. Workflow Monitoring
  обновляет дашборд при изменении его конфигурации; при изменении источников метрик он ждёт
  завершения соответствующего Infrastructure или Deploy release.
- **Успешное обновление дашборда требует живых источников.** Monitoring проверяет свежесть
  серий Linux, Django и PostgreSQL и соединение exporter с БД, затем обновляет дашборд через
  API и проверяет результат чтением. Совпадающая конфигурация не перезаписывается. Так наличие
  графиков не подменяет проверку поступления метрик.

Этот контур описывает метрики и дашборды. Внешняя проверка доступности и доставка уведомлений
имеют отдельные границы ответственности; отложенная работа отражена в
[реестре будущих изменений](future-work/2026-10-25-restore-production-monitoring.md).
Подтверждённый статус находится в [инженерном реестре](engineering-jobs.md).

## Ответственность модулей

| Область | Ответственность |
| --- | --- |
| Каталог и загрузка | Мероприятия, публикация, права фотографа и приём снимков. |
| Медиа и обработка | Закрытые файлы, производные, задания и результаты worker. |

Это логические части монолита, а не отдельные сервисы.

<a id="photo-ingestion-and-indexing"></a>
## Загрузка и обработка

Фотограф загружает оригиналы в закрытое хранилище; Django принимает их и ставит долговременные
задания. Worker возвращает результат через закрытый API, а Django проверяет и публикует
производные. Решения: [ADR 0013](adr/0013-use-direct-private-object-storage-ingestion.md),
[0017](adr/0017-use-django-polled-photo-processing-jobs.md) и
[0035](adr/0035-use-django-polled-yandex-disk-import.md).

<a id="search"></a>
## Поиск

Номер и лицо ищутся только среди доступных фотографий одного мероприятия. Поиск по лицу
сравнивает совместимые векторы AdaFace в PostgreSQL; результат остаётся снимком вероятных
совпадений, а не подтверждением личности. Решения:
[ADR 0019](adr/0019-use-public-event-selfie-search.md),
[0040](adr/0040-use-pgvector-for-exact-face-search.md) и
[0054](adr/0054-retire-sface-and-fix-adaface-vector-dimension.md).

<a id="purchase-and-download"></a>
## Покупка и выдача

Корзина выбирает фотографии, заказ фиксирует состав и цену, а подтверждённая оплата создаёт
право на закрытый оригинал. Возврат браузера с платёжной формы оплату не подтверждает.
Решения: [ADR 0029](adr/0029-use-watermarked-previews-for-paid-photos.md),
[0031](adr/0031-use-orders-and-adapters-for-paid-original-delivery.md) и
[0047](adr/0047-separate-order-payment-from-new-cart-selection.md).

## Границы доступа и данных

Оригиналы остаются закрытыми; краткоживущая выдача следует после проверки полномочий. Секреты
хранятся в Yandex Lockbox, а не в Git. Наличие кода не означает публичную активацию функции:
для незавершённых путей используются runtime gates. Решения:
[ADR 0015](adr/0015-allow-anonymous-free-event-original-delivery.md),
[0020](adr/0020-use-signed-direct-object-storage-media-delivery.md) и
[0028](adr/0028-operate-one-canonical-deployment.md).

<a id="secrets-and-ssh-access"></a>
### Секреты приложения и SSH-доступ

Схему секретов приложения, их потребителей и OIDC-идентичность задаёт
[`deploy/environment-secrets.json`](../deploy/environment-secrets.json). Resolver
[`scripts/run-with-environment-secrets.py`](../scripts/run-with-environment-secrets.py) получает
из Lockbox только разрешённый выбранному потребителю набор. Приложение не обращается к Lockbox
самостоятельно. Перечень полей и потребителей поддерживается в manifest без отдельной таблицы
в документации.

Для SSH используются ровно две пары: единая техническая для `deploy` во всех пайплайнах и
административная для `petrnikitin`. Обе хранятся в отдельных Lockbox secrets и устанавливаются
на все Terraform VM. Источники, ожидаемые пользователи и потребители заданы в `ssh_credentials`
общего manifest; получение выполняет тот же resolver, что обслуживает приложение.

Service accounts Infrastructure и приложения имеют `lockbox.viewer` и `lockbox.payloadViewer`
только на техническом секрете. CI не получает административный ключ. Оператор использует свою
учётную запись ЯО. Публичный `INFRA_SSH_PUBLIC_KEY` доступен как repository variable и в
Environment `infrastructure`; административный публичный ключ — в этом Environment.
Приватные ключи не попадают в Git, GitHub Secrets, Terraform state, логи или артефакты;
resolver создаёт файлы `0600` только на время команды и удаляет их после завершения.

Завершение создания VM сверяет её ED25519 host key через стандартные OpenSSH-утилиты с
аутентифицированным serial output и сохраняет открытый ключ в metadata `findme-ssh-host-key`.
Обычные запуски берут текущий IP и сохранённый ключ из структурированного Compute API;
повторное обнаружение не выполняется. Terraform игнорирует только это вычисленное поле.
Процедура оператора — [административный SSH-доступ](runbooks/environment-secrets.md#ssh-keys-infrastructure).
