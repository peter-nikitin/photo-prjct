# Terraform для восстановления минимальной инфраструктуры FindMe Photo

Дата: 2026-10-25. Это исследование возможностей инструментов, а не инвентаризация облака и не план применения. Исходные условия задачи: организация → облако `findme-photo` (`b1gmcsmr51o5kvp86l55`) → каталог `core` (`b1g2qttgfhb4gdunvlge`); старые VM утрачены; создаётся одна новая VM с Compose (PostgreSQL, web, workers, Nginx, imgproxy). Существующие `hires-staging`, `findme-photo-public-media-b1g2qttg`, Lockbox `e6q85jjl76r45maigtfb`, адрес `111.88.151.64`, CDN `img.findme-photo.ru`, Certificate Manager, KMS и selfie bucket, IAM, Monitoring, Postbox и внешняя DNS-зона NIC.ru требуют отдельной сверки фактических ID и настроек. Принят дамп БД; обратная совместимость и откат к старым VM не требуются.

## Вывод

Terraform подходит для описания и review облачного ядра: новая VM, диски и сеть, привязка уже зарезервированного адреса, существующие бакеты и секрет как ссылки или импортируемые ресурсы, CDN, сертификаты, KMS, service accounts и IAM. `terraform plan` показывает предполагаемые изменения до `apply`; импорт существующего ресурса требует одновременно `import` и соответствующий `resource`, а после импорта нужно проверить отсутствие непреднамеренной замены или изменения. **Полного покрытия текущей системы одним Yandex provider нет**: каталог провайдера содержит Monitoring dashboard, но не workspace, alerts, Prometheus rules/Alert Manager или Postbox. [HashiCorp: plan](https://developer.hashicorp.com/terraform/cli/commands/plan), [HashiCorp: import](https://developer.hashicorp.com/terraform/language/import/single-resource), [каталог Yandex provider](https://github.com/yandex-cloud/terraform-provider-yandex/blob/master/catalog.yaml).

## State, секреты и review

Yandex документирует удалённый `backend "s3"` на `storage.yandexcloud.net` с `skip_region_validation`, `skip_credentials_validation`, `skip_requesting_account_id`, `skip_s3_checksum`. Бакет state и доступ к нему должны существовать **до** инициализации основного state; это отдельный bootstrap, не ресурс того же ещё не инициализированного состояния. Желателен выделенный закрытый бакет с versioning и ограниченным доступом к ключу state. [Yandex: state в Object Storage](https://yandex.cloud/en/docs/tutorials/infrastructure-management/terraform-state-storage), [HashiCorp: S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3).

`sensitive = true` скрывает значение в CLI, но не удаляет его из state и plan. Сохранённый `terraform plan -out` содержит конфигурацию и значения, поэтому его нельзя класть в Git или публиковать как открытый CI artifact. Ключи backend передавать через переменные среды/защищённый runtime; пароли приложения и Lockbox payload не вставлять в HCL, `user_data`, outputs или планируемые ресурсы, пока не доказано, что конкретный аргумент не сохраняет их. [HashiCorp: sensitive data](https://developer.hashicorp.com/terraform/language/manage-sensitive-data), [HashiCorp: plan](https://developer.hashicorp.com/terraform/cli/commands/plan), [HashiCorp: S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3).

В актуальном Terraform S3 backend есть `use_lockfile = true`: он создаёт `.tflock` через условный `PutObject` (`If-None-Match: *`) и требует `GetObject`, `PutObject`, `DeleteObject` для lock-файла. Yandex Object Storage документирует `If-None-Match: *` для `PutObject`, однако HashiCorp тестирует S3 backend только с Amazon S3 и прямо называет другие S3 реализации *best effort*. Документации, подтверждающей **сквозную работоспособность native locking именно с Yandex Object Storage**, не найдено. Перед параллельными `plan/apply` нужна проверка конкурирующих запусков на выделенном тестовом state; пока это **непроверенный риск**, а не гарантированная блокировка. Старое руководство Yandex с YDB/Document API само предупреждает о deprecated DynamoDB locking в Terraform ≥1.11. [HashiCorp: S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3), [HashiCorp: реализация lock](https://github.com/hashicorp/terraform/blob/main/internal/backend/remote-state/s3/client.go), [Yandex: условная запись](https://yandex.cloud/en/docs/storage/s3/api-ref/object/upload), [Yandex: YDB locking](https://yandex.cloud/en/docs/ydb/tutorials/terraform-state-lock).

Рабочий review: конфигурация и import-блоки в Git → `terraform plan` после чтения актуального state → проверка всех `update/replace/delete`, особенно бакетов, Lockbox, IAM и адреса → только затем `apply` той же одобренной конфигурации. Для CI отдельно разграничить право читать state/делать plan и право apply; сохранённый бинарный plan передавать лишь в защищённом контуре. [HashiCorp: import](https://developer.hashicorp.com/terraform/language/import/single-resource), [HashiCorp: plan](https://developer.hashicorp.com/terraform/cli/commands/plan).

## Граница VM и данных

В текущем репозитории выпуск приложения выполняют `.github/workflows/deploy.yml`, `deploy/run-remote.sh` и `deploy/apply-deployment.sh`, а подготовка сервера частично представлена shell/Python-установщиками. Предлагаемая граница: Ansible владеет пакетами, пользователями, каталогами, systemd и подготовкой серверных компонентов; Compose описывает контейнеры; прикладной Deploy выпускает выбранные образы, выполняет миграции и проверки. Обновление этой схемы под одну VM входит в реализацию. Адрес и несекретные параметры для Ansible можно получать из Terraform outputs.

Для пакетов и systemd подходят стандартные `ansible.builtin.apt` и `ansible.builtin.systemd_service`. Проверка `--check --diff` зависит от конкретных модулей; `community.docker.docker_compose_v2` поддерживает check mode, не поддерживает diff mode, а `state=restarted` и `recreate=always` не идемпотентны. Поэтому проверка Ansible не является общим точным аналогом Terraform plan. [APT](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/apt_module.html), [systemd](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/systemd_service_module.html), [check/diff](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_checkmode.html), [Compose v2](https://docs.ansible.com/projects/ansible/latest/collections/community/docker/docker_compose_v2_module.html).

**Terraform + Ansible** — наиболее прямой долгосрочный вариант при сохранении существующего Compose и повторяемом изменении пакетов, пользователей, файлов и systemd на одной VM. Terraform отвечает за облачные объекты; Ansible — за конфигурацию ОС. Владельцем выпуска образов и запуска приложения должен оставаться один существующий релизный процесс, без второго конкурирующего `compose up` в Ansible. Проверка и diff у Ansible имеют собственные ограничения; Compose-модуль следует оценить отдельно. [HashiCorp: post-apply operations](https://developer.hashicorp.com/terraform/language/post-apply-operations), [Ansible: builtins](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/systemd_service_module.html), [Ansible: Compose v2](https://docs.ansible.com/projects/ansible/latest/collections/community/docker/docker_compose_v2_module.html).

**Terraform + cloud-init** тоже жизнеспособен надолго, если VM считается заменяемой целиком и её начальная настройка не требует регулярного in-place согласования; Terraform передаёт boot-time user data. При локальном PostgreSQL нужна независимая от boot-диска судьба данных и отдельно отработанное восстановление после замены VM. Для данного Compose-хоста с текущими обновлениями Ansible выглядит проще для обслуживания, но выбор надо сверить с фактическим релизным процессом. [HashiCorp: cloud-init](https://developer.hashicorp.com/terraform/language/post-apply-operations), [Yandex: VM и boot/secondary disks](https://yandex.cloud/en/docs/terraform/resources/compute_instance).

**Бизнес-данные вне описания инфраструктуры:** наличие ресурсов в HCL и playbook само по себе не обеспечивает восстановление строк PostgreSQL, содержимого S3 media, Lockbox payload или права на домен. Ansible может запускать восстановление, но для него нужны сохранённый источник данных и отдельная явная операция. Принятый dump надо восстановить и проверить; наличие и читаемость медиа подтверждены ранее отдельной проверкой действующих бакетов. Наличие bucket/VM в `plan` доказывает только конфигурацию ресурсов, не восстановление пользовательского сервиса. [Yandex: Object Storage хранит объекты](https://yandex.cloud/en/docs/storage/concepts/object), [HashiCorp: Terraform state описывает ресурсы](https://developer.hashicorp.com/terraform/language/state).

Открытые проверки перед реализацией: фактические IDs/настройки ресурсов и IAM; отсутствие destructive plan при импорте; параметры state bucket и его bootstrap; совместимость lockfile; workflow для Monitoring и Postbox; фактический способ обновления Compose; судьба диска PostgreSQL и проверка restore/media. Этот список фиксирует пробелы исследования, а не утверждение о текущем состоянии облака.
