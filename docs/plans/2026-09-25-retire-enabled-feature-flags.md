## Goal

Implement the approved specification's permanent enabled behavior and remove all eight obsolete
switches in one release without changing the independent authorization, paid-product, worker,
storage, or durable-state contracts.

## Scope

The plan implements the approved specification without scope changes.

## Acceptance criteria

The approved specification's acceptance criteria apply. In addition, the cutover is accepted only
when the final package and canonical environment contain no retired names, startup reconciliation
deletes only the two retired rows, the before/after durable-state inventory matches except for
ordinary concurrent production progress, and all selected verification suites are green for the
same final package fingerprint.

  processing leases, no import batches/items/attempts/content, and only terminal processing jobs.
  The retained processing identities are contract 1 `capture_metadata` v1/v2 and

  and `generate_watermarked_preview` v1; and contract 3 `face_embedding_benchmark` v1, with their
  persisted configuration hashes left unchanged. Published artifacts are 87,146
  `preview-small-v1` and 4 `preview-watermarked-v1`. Photo policies are 115 legacy-original,
  87,143 preview-first, and 4 watermarked-preview photos. Relevant prefixes remain
  `incoming/`, `processing-pending/previews/`, published derivative keys, and the existing
  feedback-object prefix generated by `SelfieFeedbackStorage`; this release neither enumerates nor
  mutates objects. Before cutover, repeat the same ORM aggregate and stop if any non-terminal state,
  active/expired lease, new processor identity, or import work appears without a reviewed drain
  decision.
- [x] **Compatibility matrix.** Old Django + old workers + old rows is the current deployment. New
  Django + old workers + old rows is supported because request URLs, bearer tokens, payloads,
  contract versions, processor identities, and lease semantics do not change. New Django + new
  workers + old rows is supported for the same reason; existing terminal rows and derivatives
  remain readable and any ordinary queued/retryable work is processed in place. New Django + new
  workers + new rows is the permanent behavior. Rolling back to old Django/workers preserves all
  rows and objects; restored definitions are reconciled as `off`, and removed environment values
  are not silently reconstructed.
- [x] **Reviewed data-state migration or reset semantics.** Use compatible retention. There is no
  schema migration, state reset, requeue, backfill, replay, supersession, or artifact purge.
  Persisted legacy photo policies remain legacy, terminal attempts remain immutable, published
  derivative identities remain unchanged, feedback rows/objects remain untouched, and ordinary
  lease/retry rules govern any work that appears after the snapshot.
- [x] **End-to-end contract sizing.** The representative upper-bound worker result is the existing
  128 KiB `ProcessingAttempt.result`; retain its worker serialization and HTTP client, the 25 MiB
  Nginx ceiling, the narrower 384 KiB Django request ceiling, callback validation, 128 KiB model
  validator, and PostgreSQL persistence without edits. Focused model/view tests must still accept
  the exact bounded result inside its request envelope and reject the first oversized result or
  request. Import retains its independent 1 MiB JSON request, 10,000-entry manifest, and 50 MiB
  object limits. No changed code may increase any limit or add a second serialization.
- [x] **Previous-snapshot upgrade rehearsal.** No schema or protocol change is present, so rehearse
  with the existing fixture surfaces rather than transforming data: processing model/view/job
  tests cover successful, failed, retryable, expired/stale, leased, accepted, derivative, and
  never-enrolled states; import API/flow/publication tests cover queued, active, retryable,
  expired, terminal, and published states. Run those tests against the candidate after removing
  gates. Before deployment, clone the current deployed database with
  `scripts/clone-deployed-db.sh`, start only the candidate database/web topology, run
  `manage.py migrate --plan`, `manage.py migrate`, `manage.py sync_feature_flags`, and the same
  read-only aggregate. Expected outcome: no application rows or artifacts are changed, exactly the
  two stale flag rows disappear, all existing state remains readable, and Django checks pass.
- [x] **Staged activation and rollback order.** The user selected one atomic application cutover,
  so there is no partial public cohort. Build and verify the entire candidate, repeat the live
  inventory, require no active leases/non-terminal imports, deploy web and the ordinary import,
  bulk, and selfie workers together, run startup reconciliation, verify health/storage/auth/product
  probes, then remove the six GitHub variables. Stop before traffic cutover if mandatory storage or
  credential validation fails, a retired name remains in the candidate environment, a new state
  class appears, or reconciliation would delete any other flag. After cutover, stop affected worker
  services for runaway computation or deploy the prior successful image for application failure;
  preserve all rows and object keys. Recreating old settings/flag states is an explicit operator
  action, never part of automatic rollback.
- [x] **Supported bounded operational commands.** Inspection uses the read-only ORM aggregate in
  this plan, `python manage.py inspect_photo_imports --limit 100`, existing processing reports,
  Compose `ps`, and storage verification commands. Reconciliation uses only
  `python manage.py sync_feature_flags` and must report exactly two deleted model rows on first
  candidate start. No requeue, backfill, replay, reset, or purge command is authorized. A service
  stop is bounded to `import-worker`, `worker-bulk`, or `worker-selfie`; database and Object Storage
  deletion commands are outside this plan.

## Rollback

For a computation incident, stop only the affected `import-worker`, `worker-bulk`, or
`worker-selfie`; leave PostgreSQL, Object Storage, and unrelated services intact. For web/product
failure, redeploy the prior successful image. The prior image will recreate the two definitions as
`off`; because the six GitHub variables are deleted after candidate verification, it will also see
the old Django switches as false unless an operator deliberately restores them. Preserve every
upload, import, processing attempt, photo policy, derivative, feedback row/object, archive audit,
and media object. Never reset, requeue, backfill, or purge as part of rollback.

If continued operation of the prior image is explicitly chosen, restore old environment values and
the two DB states only through a separately reviewed operator action after diagnosing why disabled
old behavior is insufficient. Rolling forward with a corrected permanent implementation is the
preferred recovery.
