# 0065: Проверять публичную доступность вне VM бессерверной функцией

- Status: Proposed
- Date: 2026-11-10
- Deciders: владелец проекта; размещение ожидает подтверждения в PR
- Supersedes: [ADR 0039](0039-run-public-probe-on-image-origin-vm.md), только размещение probe
- Superseded by: none

## Контекст

Приложение, обработчики и image origin работают на одной VM. Прежняя отдельная image-origin
VM остановлена, поэтому размещённый на ней внешний probe больше не публикует наблюдения.
Проверка внутри самой VM не обнаруживает её сетевую недоступность для клиента. Существующее
измерение расписания GitHub Actions в ADR 0039 показало интервалы 100–403 минуты; такой
источник не подходит для оповещения об отказе в течение нескольких минут.

## Мотивы

- Проверять публичные DNS, доверие TLS, HTTP и ответ health независимо от VM приложения.
- Сохранять минимальную постоянную стоимость и существующие каналы уведомлений.
- Описывать ресурсы и права в Terraform, выпускать изменения через PR и общий merge→release.
- Отделять наблюдённый отказ сайта от отсутствия наблюдений и ошибок публикации метрик.

## Варианты

1. Вернуть отдельную постоянно работающую VM для probe: дополнительные постоянные расходы
   и обслуживание ОС ради одного короткого запроса.
2. Использовать Cloud Function с минутным таймером: отдельного хоста нет, сохраняются IAM,
   существующий Prometheus и каналы ЯО; общий отказ облака остаётся слепой зоной.
3. Использовать внешний managed checker: независимость от отказа ЯО, но дополнительный
   поставщик, учётная запись, интеграция уведомлений и условия обслуживания.

## Решение

Предлагается вариант 2. Минутный таймер вызывает закрытую Cloud Function, которая проверяет
`https://findme-photo.ru/health/` через публичный DNS и доверенный TLS, затем публикует исход
проверки, длительность и время наблюдения в существующий Managed Prometheus.
Alertmanager продолжает отправлять критические уведомления и восстановление в существующие
email и Telegram. Функция не получает SSH, доступ к БД, медиа или ключи приложения.

Для публикации используется краткоживущий IAM-токен отдельного служебного аккаунта из контекста
вызова, без постоянного API-ключа. Ресурсы функции, таймера и необходимые IAM-права находятся
в Terraform. Архив исходного кода передаётся вместе с рассмотренным сохранённым plan, чтобы
применялся именно одобренный пакет, без отдельного манифеста SHA merge-коммита.

Наблюдённые DNS/TLS/HTTP-ошибки означают отказ проверки. Ошибка отправки метрик означает
неизвестное состояние, а не поддельный отказ сайта. Мониторинг не перезапускает сервисы,
не меняет очереди и не выполняет автоматическое восстановление.

## Последствия

Отпадает обслуживание отдельной VM, а замена приложения не затрагивает внешний checker.
Появляется небольшой расход на вызовы и исполнение функции, а также запись метрик.
Постоянный отказ самого ЯО или мониторинга может лишить оператора наблюдений без отдельного
уведомления; такая граница уже принималась в ADR 0039. Требование независимости от облака
станет основанием пересмотреть размещение в пользу внешнего сервиса.

## Проверка

Подтвердить минутные свежие точки, успешный HTTPS-проход и контролируемое firing/recovery
в обоих каналах без остановки сайта. Отдельно проверить ошибку публикации: она не должна
превращаться в успешное наблюдение или в ложную недоступность сайта.
Применение новых ресурсов и IAM выполняется только после рассмотрения конкретного Terraform
plan и сметы. Принятие этого ADR и разрешение на создание ресурсов — отдельные подтверждения.
