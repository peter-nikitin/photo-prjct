# Нагрузочные сценарии FindMe Photo

`gallery-journeys.js` воспроизводит HTTP-запросы публичного пользователя: формы галереи,
загрузку изображения, polling поиска и кнопки готового результата. Это протокольный тест k6,
не браузерный тест JavaScript/отрисовки. Контракты кнопок сверены с
`selfie-search.js`, `search-result-feedback.js`, шаблоном результата и обработчиками Django.

## Сценарий сравнения

| Сценарий | Действие после открытия мероприятия | Визитов/мин при PROFILE=300 |
| --- | --- | ---: |
| `pagination` | Переход на вложенную страницу галереи | 90 |
| `folder` | Фильтр по одной или нескольким папкам | 45 |
| `time` | Фильтр по времени съёмки | 30 |
| `folder_and_time` | Совместный фильтр | 30 |
| `gallery_face` | Кнопка поиска лица из галереи | 30 |
| `selfie` | Загрузка селфи, ожидание результата | 15 |
| `find_more` | Поиск из галереи → «Найти ещё» | 15 |
| `find_by_result` | Поиск из галереи → «Найти по этому фото» доступной карточки | 15 |
| `add_selfie` | Поиск по селфи → «Добавить селфи» → «Найти по этому селфи» | 15 |
| `negative_feedback` | Поиск из галереи → «Это не я» → отмена отметки | 15 |

`PROFILE=60` уменьшает каждый темп в пять раз. `smoke` проверяет каждый case один раз.
При 300 визитах 105 посетителей запускают первоначальный поиск, ещё 45 действий создают
дополнительный проход. Это отличается от старого сценария с 20% первоначальных поисков.
Приходы распределены по минуте; одновременный старт 300 человек этот профиль не моделирует.
`JOURNEY=<имя>` выбирает один сценарий с его исходным темпом.

Каждое открытие HTML включает до шести видимых превью (`PREVIEW_COUNT=0..20`, по умолчанию6).
Кнопки продолжения используют JSON Accept, hidden-поля формы, CSRF, Origin и выбранный
`photo_id`, как JS сайта. Для дополнительного селфи передаётся актуальный `upload_count`.
Polling2s совпадает с клиентом; после готовности проверяется ожидаемая `data-photo-id`.
«Найти ещё» с ответом `more=unavailable` считается ошибкой fixture, а не успешным поиском.
Отметка «Это не я» меняет только созданный тестовый поиск и затем снимается новым submission ID.
Как в JS, перезагрузка результата происходит только при изменении числа исключённых фото.
Дополнительный проверочный запрос статуса подтверждает успех дочернего прохода даже если родитель
уже готов; этот запрос учитывается в HTTP-нагрузке обоих прогонов.
Загрузка оригиналов, ZIP, корзина и оплата в этот профиль не входят.

## Мероприятие и контрольные данные

Зафиксированный набор `cases/championship-290826.json` относится только к мероприятию
«Велоспорт - Чемпионат России среди любителей 2026 (Раздельный старт)»,
`cycling-russian-amateur-championship-290826`. Перед тестом проверить публичные флаги:
`face-search-anchor-expansion=on`, `apparel-search-expansion=on`, `selfie-search-passes=on`.
Проверить подготовку лиц и одежды на всех фотографиях и участие расширений в новых проходах.

Изображения и результаты не коммитятся: `tests/load/.local/` игнорируется.
Для текущего набора нужен `.local/participant.jpg`: контрольное изображение одного участника
из большого превью первой карточки страницы111. Исходный screenshot из предыдущего теста
не дал совпадений на этом мероприятии. Контрольное изображение проверено реальной загрузкой;
оно упражняет путь селфи, но не представляет разнообразие селфи с телефонов.
Cases содержат SHA256 изображения; k6 отвергает подмену снимка или мероприятия. Для другого снимка сначала подобрать и проверить
свой `expectedPhotoId`; не подменять fixture между замерами.

Поля cases: `page`, `folders`, `from`/`to` (часовой пояс мероприятия), `detectionId`,
`expectedPhotoId`; для selfie/add_selfie — относительный от скрипта `file`.
Для поиска по результатам должны существовать пригодные новые опоры.
Подписанные URL, приватные URL результатов и токены в cases не записывать.

## Запуск

Из корня checkout с установленным k6:

```sh
export BASE_URL=https://findme-photo.ru
export EVENT_SLUG=cycling-russian-amateur-championship-290826
export JOURNEY_CASES_FILE="$PWD/tests/load/cases/championship-290826.json"
PROFILE=smoke k6 run --log-output none tests/load/gallery-journeys.js
PROFILE=60 k6 run --log-output none tests/load/gallery-journeys.js
PROFILE=300 k6 run --log-output none tests/load/gallery-journeys.js
```

На проде сначала smoke. Большую нагрузку подавать при здоровом `/health/`, под наблюдением
CPU/RAM/диска и очередей. Прервать при двух последовательных сбоях здоровья, дождаться
завершения уже принятых задач. Генератор на ноутбуке не использует CPU сервера; состояние сети
ноутбука влияет на замер. Порядок замеров, исходная конфигурация и возврат описаны в
[runbook](../../docs/runbooks/search-capacity.md).

Сохранить `--summary-export` и при необходимости `--out json=...` в `.local/`, версии k6,
SHA кода/сценария/cases/изображения, UTC-окно и флаги. В до/после использовать одинаковые
данные, профиль и прогрев. Изменение сценария требует нового baseline.

Успех: все cases проходят, `journey_failed=0`, `dropped_iterations=0`, ожидаемое число
визитов завершено. Встроенные стартовые пороги: HTML p95<2s, поиск p95<60s, ошибки<1%.
Они выявляют деградацию и не являются обещанием такой скорости. Сравнивать длительности
каждого journey и `search_ready_ms` с тегом `action`; различать первоначальный поиск и кнопки.
Проверять отсутствие накопившейся очереди и реальное завершение дочерних поисков.
Метрика `test_searches` содержит только необратимый digest созданного родительского поиска:
по нему выбирать в БД семейства теста, чтобы параллельный трафик людей не искажал результат.

`event-announcement.js` сохраняет прежний отдельный профиль просмотра и скачивания
бесплатного оригинала, с `FACE_CASES_FILE` (массив detectionId/expectedPhotoId),
`PROFILE=smoke|300|600`, `BASE_URL`, `EVENT_SLUG` и `PREVIEW_COUNT`. Он не используется
в текущем сравнении конфигураций и не покрывает селфи/продолжения.
