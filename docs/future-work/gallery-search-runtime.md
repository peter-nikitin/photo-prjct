# Производительность поиска на текущей ВМ

8 ноября 2026 года поиск по текущим векторам события 16 проверен без выкладки.
Обычный read-only SELECT с лимитом 20 секунд не завершался. Без statement_timeout
вариант с сырым SQL завершился за 39,53 секунды и нашёл 21 фотографию.

После замены ранжирования на Django ORM выполнен парный замер на том же исходном
векторе и одном REPEATABLE READ, READ ONLY снимке данных, без ограничения времени:

| Вариант | Время |
| --- | ---: |
| Сырой SQL | 34,16 с |
| Django ORM | 111,93 с |

В обоих случаях проверены 17 467 лиц на 14 737 фотографиях, найдено 21 совпадение,
включая исходную фотографию. Полный упорядоченный результат совпал, разность
расстояний — 0. Это одна пара запусков в порядке SQL → ORM, не оценка под нагрузкой.
ORM выполнялся после SQL и мог использовать прогретый кеш; подтверждения ускорения нет.

Дополнительные обычные ORM-запуски: 100,58 и 93,29 секунды. В обоих случаях
счётчики и 21 совпадение сохранены; полный упорядоченный результат повторов совпал.

Диагностика `EXPLAIN (ANALYZE, BUFFERS)` на том же снимке:

- SQL: 32,53 секунды; набор `scored` с 17 467 лицами вычисляется один раз.
- ORM: 95,55 секунды; подсчёт занимает 40,33 секунды, выдача — 55,11 секунды.
- ORM делает два полных параллельных прохода по таблице детекций: отдельно для
  подсчёта и выдачи. SQL использует индексные выборки детекций нужного события.
- Запрошено чтений shared-блоков: 125 942 у ORM против 32 530 у SQL. Это промахи
  кеша PostgreSQL, а не утверждение о физических чтениях диска: кеш ОС также возможен.
- Коррелированный подзапрос получения photo_id выполнен 34 934 раза.
- JIT у ORM занимает 239,719 мс, временных блоков ORM не читает и не пишет.
  JIT и выгрузка сортировки во временные файлы не объясняют основное замедление.

Времена с EXPLAIN приведены отдельно от обычных запусков: диагностика добавляет
накладные расходы. Тяжёлая работа повторяется в форме сгенерированного ORM SQL;
это не доказательство, что Django ORM в принципе должен быть медленнее.

## Оптимизация ORM от состояния фотографии

ORM перестроен от `PhotoProcessingState`: photo_id берётся из самой строки,
лица и векторы присоединяются через обычные ORM связи. Построчный подзапрос
photo_id убран. JOIN попытки служит только связью по PK, без чтения полей
происхождения/результатов и проверки цепочки обработки. Новые зависимости,
индексы и изменения схемы не добавлялись.

Две пары обычных read-only запусков на том же событии/векторе:

| Порядок | SQL | Оптимизированный ORM |
| --- | ---: | ---: |
| SQL → ORM | 36,62 с | 40,44 с |
| ORM → SQL | 28,64 с | 36,65 с |

В каждой паре использован один REPEATABLE READ snapshot. Счётчики, полный
упорядоченный результат и расстояния совпали точно: 17 467 лиц, 14 737 фотографий,
21 совпадение, максимальная разность расстояний — 0. Это два контрольных запуска,
не измерение под параллельной нагрузкой. Старый разрыв примерно в три раза снят;
новый ORM в этих парах медленнее SQL на 10–28%.

Актуальный state-rooted ORM дополнительно проверен через EXPLAIN ANALYZE:
42,73 секунды, из них подсчёт — 11,64 секунды, выдача — 31,09 секунды.
JIT отсутствует, временные блоки не читаются и не пишутся. Shared reads —
44 146 блоков. У vector установлен attstorage=external; размер основной таблицы
векторов — 67 633 152 байта, с TOAST/FSM/VM — 478 003 200 байт. Это основание
проверить стоимость хранения и чтения на копии данных, а не обещание эффекта
от смены STORAGE без замера. Схема и настройки не менялись.

На момент этих измерений лимит приложения составлял 20 секунд; оба варианта
его превышали. Результаты поиска, приложение и схема БД на сервере не менялись.

Триггер возвращения к задаче — подготовка выкладки поиска. Нужно определить
допустимое время ответа под нагрузкой и проверить полный сценарий сайта. Старый разбор выше относится к уже заменённой ORM-форме;
дальнейшую оптимизацию нужно основывать на плане актуального state-rooted запроса.

## Кеш счётчиков в памяти

По согласованному упрощению два числа корпуса кешируются через Django LocMemCache
на 60 секунд, отдельно для события и модели. Векторы и результаты не кешируются.
На попадании полный COUNT не выполняется; свежие совпадения и Exists подходящих
векторов получаются одним ORM statement. Именно Exists определяет наличие корпуса,
поэтому устаревшие числа не влияют на выдачу и статус поиска. Числа в результате —
последний замер, который на момент поиска может отставать до минуты. Кеш отдельный
для каждого процесса и сбрасывается при его перезапуске.

Контрольный запуск без выкладки в одном отдельном Python-процессе, READ ONLY,
REPEATABLE READ, без ограничения времени, на прежнем событии и исходном векторе:

| Вариант | Время |
| --- | ---: |
| Прежний ORM с подсчётом на каждом поиске | 45,32 с |
| Новый ORM, промах кеша | 47,35 с |
| Новый ORM, подтверждённое попадание в кеш | 27,70 с |

Везде 17 467 лиц, 14 737 фотографий, 21 совпадение. Полные упорядоченные результаты,
включая расстояния, совпали точно. Повторный вызов быстрее контрольного на 38,9%.
Это один последовательный прогон, а не изолированное измерение эффекта кеша:
прогрев PostgreSQL и ОС тоже мог повлиять. Холодный вызов требует подсчёта и
не ускоряется. Все замеры превышают прежний лимит 20 секунд. Для выпуска согласован
SQL-таймаут 120 секунд, ожидание upstream в Nginx увеличено до 150 секунд. Измеренные
запуски укладываются в новый лимит; сценарий под параллельной нагрузкой ещё не проверен.
Триггер дальнейшей оптимизации — неприемлемое время ответа или конкуренция поиска
с другими запросами на рабочем сайте. Код и данные на сервере при замерах не менялись.


## Интеграция очереди

В локальном пакете поиск перенесён из HTTP process POST в один постоянный Django-worker.
Оптимизированный ORM по текущим accepted vectors и кешируемые приблизительные счётчики
сохранены. Только ранжирование получает SQL-бюджет 120 секунд; вне него действует 30 секунд,
а watchdog процесса — 150 секунд. Предыдущие замеры остаются измерениями прежнего пути;
интеграция очереди ещё не развёрнута и не проверена под нагрузкой на production VM.
