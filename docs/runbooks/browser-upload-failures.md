# Ошибки браузерной передачи оригиналов

Область — прямой POST из браузера в Object Storage и подтверждение оригинала в Django.
Обработка и публикация производных диагностируются отдельно.

Координатор ограничивает передачу четырьмя POST, подтверждение четырьмя запросами и весь
незавершённый конвейер восемью файлами. Ожидание повторной попытки входит в этот предел.
После успешного POST следующий файл может передаваться, пока предыдущий подтверждается.

## Коды и свидетельства

В `UploadItem.error_code` сохраняется безопасная причина окончательной ошибки передачи:

| Код | Что наблюдал браузер |
| --- | --- |
| `transfer_http_error` | HTTP-ответ хранилища; повторный 403 после обновления разрешения также попадает сюда. |
| `transfer_network_error` | Событие XHR `error` без доступного HTTP-ответа. Оно само по себе не устанавливает сетевую причину. |
| `transfer_timeout` | Истечение тайм-аута XHR. |
| `transfer_cancelled` | Отмена текущей попытки пользователем. |

После принятого запроса `failed` web-приложение пишет JSON-сообщение с `event=browser_upload_failed`.
Для сопоставления доступны `batch_id` и `item_id`. Диагностика содержит только `error_code`,
`http_status` (0 при отсутствии HTTP-ответа), `post_attempts` и `post_duration_ms`.
Счётчик отражает фактические вызовы POST, включая повтор после обновления разрешения при 403;
он отличается от серверного счётчика разрешений на передачу. Длительность суммирует только
POST текущего цикла, без ожидания разрешений, backoff и подтверждения. Длительность ограничена
600 000 мс, число POST — пятью. После ручного повтора начинается новый цикл измерений.
URL, имя файла, тело ответа, поля подписанного разрешения и credentials в сообщение не входят.
Запросы с лишними полями или неверными типами/пределами отклоняются до изменения состояния.

Искать сообщение можно в обычных логах web-контейнера по `browser_upload_failed`, затем по
идентификатору партии или элемента. Исторические строки с `transfer_retries_exhausted`
не позволяют восстановить HTTP status или первопричину: новая диагностика к ним не добавляется.

## Повтор и восстановление

При окончательной ошибке передачи пользователь видит причину рядом с файлом и может повторить
его через существующую кнопку. Если сеть недоступна и отчёт `failed` не записан, причина и
диагностика остаются в памяти страницы, а кнопка повтора остаётся доступна. Повтор сначала
идемпотентно сохраняет тот же отчёт, затем запрашивает новую попытку передачи. До записи
отчёта финализация и следующие передачи партии приостановлены. Успешные элементы партии
повторно не передаются.

При потере ответа подтверждения браузер повторяет `confirm`, сохраняя уже переданные байты.
После исчерпания ограниченных попыток файл остаётся доступен для повторного подтверждения;
новые передачи этой партии приостанавливаются, а ожидающие файлы остаются в очереди.
Успешный ручной повтор подтверждения автоматически продолжает эту очередь. Финализация
не выполняется, пока результат подтверждения неизвестен. Отмена до первого запроса подтверждения записывается через `failed`, включая ожидающие
позиции возобновляемой загрузки. Отложенную из-за недоступности сервера позицию можно отменить
сразу, не ожидая восстановления остальных. Отмена уже начатого подтверждения не отменяет
возможный серверный commit; его результат выясняется повторным `confirm`. Если `failed`
сообщает, что другой запрос уже подтвердил фото, результат также согласуется через `confirm`.
Если отложен повтор уже неудавшегося элемента и новый `retry` ещё не запрашивался, отменяется
только локальный повтор: прежний серверный `failed` сохраняется, обычный повтор остаётся доступен.
Ошибка финализации после отмены обрабатывается самой страницей: очередь сохраняет конечные
состояния и показывает указание обновить страницу для проверки результата. Техническая причина
ошибки не попадает в пользовательский текст.

После перезагрузки используйте существующее возобновление загрузки с повторным выбором файлов.
Для элемента в состоянии `authorized` браузер сначала запрашивает `confirm`. Только явный
`object_missing` при этой проверке разрешает новую передачу, в том числе после ручного
повтора неудавшейся проверки; неизвестный исход не требует повторной отправки байтов.
Устаревший запрос, проигравший смене checkpoint или авторизации, получает HTTP 503
`confirmation_in_progress` и согласуется повторным `confirm` вместо финализации или `retry`. Подтверждённые элементы манифеста пропускаются.

Это процедура диагностики и пользовательского повтора. Она не предполагает массового reset,
requeue или удаления оригиналов и не обещает устранения неизвестной сетевой причины.
