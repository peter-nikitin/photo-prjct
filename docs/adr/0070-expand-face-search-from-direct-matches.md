# 0070: Расширять поиск по лицу от прямых совпадений

- Status: Accepted
- Дата: 2026-11-18
- Авторы решения: владелец проекта
- Заменяет: нет
- Заменено: нет

## Контекст

В одном мероприятии исходное лицо на селфи или фото галереи может совпадать только с частью
снимков того же участника. Прямые совпадения дают дополнительные ракурсы, от которых можно
искать ещё раз. Локальный прогон на архиве «Вечернего Садового» с опорами из кадров с одним
обнаруженным лицом вернул 7 из 13 известных пропусков в каждом из двух сценариев, когда
достаточно одного совпадения с опорой. Требование двух совпадений оставило по 5 из 13.
Наборы пересекались по участникам, большая часть новых кадров не размечена.

## Мотивы

- Применять одно правило для селфи и поиска из галереи.
- Ограничить число повторных сравнений и число обращений к PostgreSQL.
- Сохранять границы мероприятия, действующую доступность фото и происхождение результатов.
- Включать расширение отдельно от прямого поиска и поиска по кластерам.

## Рассмотренные варианты

1. Выполнять отдельный точный поиск для каждой опоры и объединять фото в приложении.
2. Выбирать опоры и сравнивать их с корпусом мероприятия одним пакетным запросом PostgreSQL.

## Решение

Выбран вариант 2. Общий исполнитель очереди сначала получает прямую выдачу. Для расширения
он выбирает до трёх кадров из прямой выдачи с расстоянием AdaFace до исходного лица не выше
0,38. В принятой попытке обработки опоры должно быть ровно одно обнаруженное лицо. При поиске
из галереи исходное фото исключается из кандидатов в опоры. Первой берётся ближайшая опора.
Каждая следующая максимизирует расстояние до ближайшей из уже выбранных опор.

Один пакетный SQL-запрос выбирает опоры и ищет новые кадры среди лиц того же мероприятия.
Кадр добавляется, если хотя бы одно его лицо находится на расстоянии не выше 0,42 хотя бы
от одной опоры. Дополнительные кадры не становятся источником следующих поисков.
Повторное совпадение одного фото не создаёт второй результат. Уже найденные прямым или
кластерным путём фото сохраняют своё место и источник. Для нового фото хранится одно лучшее
свидетельство с опорой, найденным лицом и расстоянием. Векторы остаются в PostgreSQL.

Флаг `face-search-anchor-expansion` создаётся в состоянии `off` по ADR 0032. Общий
исполнитель проверяет текущее состояние флага. Для режима `staff` он опирается на признак
доступа, который сервер сохранил при создании поиска. Отключение флага останавливает
расширение новых выдач. Сохранённые результаты остаются снимками.

## Последствия

Одна и три опоры требуют одного обращения к PostgreSQL за расширением. При этом стоимость
точного сравнения растёт с числом опор и лиц. На архивном корпусе из 38 799 векторов медиана
локального SQL-замера составила 64 мс для одной опоры и 192 мс для трёх в одном запросе.
Этот замер не включает очередь и публикацию.

Ограничение на одно обнаруженное лицо зависит от детектора. Порог 0,38 и это ограничение
снижают риск ошибки при выборе опоры. Неполная разметка эксперимента пока не позволяет
оценить долю ошибочных добавлений.

## Проверка и откат

Проверить оба входа, отсутствие роста числа SQL-запросов от одной до трёх опор, уникальность
фото, границу мероприятия, пороги, происхождение и поведение флага в режимах `off`, `staff`
и `on`. До публичного включения измерить p95 общего времени поиска на большом мероприятии
под параллельной нагрузкой и оценить размеченную выборку добавлений. Откатить расширение
можно переводом флага в `off` через Django Admin.
