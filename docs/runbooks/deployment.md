# Выпуск приложения на одной ВМ

Документ предназначен оператору FindMe Photo. Он описывает действующий интерфейс выпуска;
обновляется в одном PR с изменением Deploy. Разовое восстановление данных не является частью
обычного выпуска.

## Границы

Terraform создаёт ВМ и диски, Ansible настраивает ОС. GitHub Actions **Deploy** собирает образы
Django, photo-worker и import-worker и выпускает Compose-проект `photo-prjct` на эту ВМ.
Commerce использует образ Django. PostgreSQL хранит данные в `/var/lib/findme-photo/postgres`
на отдельном смонтированном диске. Приложение работает с существующими S3-бакетами.

На этапе восстановления прямой HTTP по IP остаётся доступным до выпуска сертификата. Код
подготавливает NLB, домены и HTTPS; их работа подтверждается отдельно после применения инфраструктуры,
DNS и выдачи сертификата. Автоматический выпуск приложения после merge проверяется отдельным
завершающим этапом; сейчас workflow вызывается вручную.

## Запуск

1. В GitHub открыть Actions → **Deploy** → **Run workflow**, выбрать рассмотренную ветку `main`.
2. Оставить `deploy=false`, чтобы только собрать и опубликовать образы. ВМ и база не меняются.
3. После проверенного восстановления базы запустить workflow с `deploy=true`.
4. Проверить результат build и deploy, затем страницу сайта и чтение восстановленных данных.

Один запуск собирает согласованный набор образов. В выпуск передаются полученные registry
**digests**; перемещение тега не меняет выбранный образ. Отдельный сохранённый план или
SHA-манифест для допуска к выпуску не требуется.

Workflow использует repository variables `VM_HOST`, `VM_USER`, `VM_SSH_KNOWN_HOSTS`.
При завершении создания или замене ВМ оператор обновляет адрес и открытый host key из
аутентифицированного API ЯО; `findme-ssh-host-key` хранится в metadata ВМ. Не получать доверенный
ключ простым `ssh-keyscan` из непроверенной сети.

Технический приватный SSH-ключ и секреты приложения получает общий resolver из Lockbox по
manifest `deploy/environment-secrets.json`. CI не читает административный ключ. Секреты
передаются по SSH через stdin, а `.env` на ВМ принадлежит root и имеет права `0600`.
Техническая учётка выполняет настройку контейнеров через `sudo -n`.

## Что делает выпуск

Выпуски сериализованы. Скрипт останавливает worker-профили, подтягивает immutable образы,
проверяет конфигурацию Commerce, запускает PostgreSQL, применяет актуальные Django-миграции,
собирает staticfiles и поднимает web и единый Nginx. Сертификаты и БД сохраняются. Это не восстановление БД: на новой ВМ сначала
нужно восстановить принятую резервную копию, затем явно запустить Deploy.

Nginx обслуживает HTTP и HTTPS и выбирает bootstrap HTTP, пока общего сертификата нет. Внутренний
listener 8081 предоставляет только `/health/`: Django выполняет `SELECT 1` и возвращает 200 или 503.
Тот же `/health/` используют Docker и публичная проверка сайта. Доступ к порту 8081 ограничивает
security group для проверок NLB. PostgreSQL и worker API не публикуются; Nginx
закрывает `/internal/`, `/metrics/` и `/worker-diagnostics/`.

CDN пока не восстановлен: origin указывает на остановленную прежнюю ВМ, поэтому превью через CDN
возвращают 504. Оба CDN gate остаются включены. Условия восстановления приведены в
[future work](../future-work/2026-11-07-restore-cdn-origin.md).

## Сертификат и домены

После применения NLB, проверки healthy target и обновления DNS сайта и www на адрес NLB
выполнить один ограниченный выпуск на ВМ:

```sh
sudo sh /opt/photo-prjct/deploy/certbot/reconcile-certificate.sh
```

Команда использует HTTP-01 webroot и email из закрытого `.env`, выпускает единый сертификат для
`findme-photo.ru` и `www.findme-photo.ru` и пересоздаёт Nginx в HTTPS
режиме. До этого сайт остаётся на bootstrap HTTP. При ошибке DNS или challenge сертификат не
выпускается и прежний HTTP edge остаётся работать. После выпуска обычный Deploy сохраняет сертификат.
Контейнер `certbot-renew` проверяет продление каждые 12 часов, Nginx перечитывает сертификат каждый
час; для проверки отдельно выполнить:

```sh
sudo docker compose --project-directory /opt/photo-prjct --project-name photo-prjct \
  --env-file /opt/photo-prjct/.env -f /opt/photo-prjct/docker-compose.deployment.yml \
  --profile acme run --rm --no-deps certbot renew --dry-run --webroot -w /var/www/certbot
```

Проверить доверенный HTTPS, редиректы, доступ к каталогу и сохранность БД. До такой проверки
не считать DNS или сертификат восстановленными; CDN остаётся отдельной незавершённой задачей.

## Воркеры во время восстановления

Профили `photo-worker`, `import` и `commerce` по умолчанию выключены. Выпуск заранее загружает
образы, но не начинает обработку восстановленной очереди. Photo-worker обращается к Django по
внутренней Docker-сети и отдельному токену; не получает прямой доступ к PostgreSQL и постоянные
S3-ключи. Восстановленная очередь и внешние побочные эффекты проверяются перед активацией.

Штатные CLI photo/import работают в цикле; Commerce `--once` также может забрать существующие
платёжные или почтовые задания. Не использовать их как безусловный smoke test. Для приёмки
нужно подтвердить безопасную область очереди и выполнить ограниченное контролируемое задание.

## Проверка и ошибки

Проверить извне `http://<VM_HOST>/` и `/health/`, открыть каталог и реальную галерею. Отдельно
выполнить запрос к БД через Django: HTTP health не заменяет проверку восстановленных данных.
Подтвердить, что внутренний API и порт PostgreSQL недоступны снаружи. Работа контейнера сама по
себе не доказывает выполнение задания воркером.

При ошибке изучить статус GitHub Actions и на ВМ — `docker compose ps`, выбранный образ,
монтирование диска и логи конкретного сервиса. Не публиковать `.env`, bearer-токены, ссылки с
доступом и персональные payload. Исправление выпускается через тот же workflow; данные не
сбрасываются и резервная копия не восстанавливается заново как побочный эффект деплоя.
