# 0057: Хранить желаемое состояние инфраструктуры в IaC и обеспечивать её переносимость

- Status: Accepted
- Date: 2026-10-25
- Deciders: владелец проекта; явно принял ADR 0056, 0057, 0058 и 0063 в обсуждении 2026-10-25
- Supersedes: none; дополняет [0051](0051-release-photo-worker-images-independently.md) и [0053](0053-reconcile-observability-independently-on-main.md) инфраструктурным путём
- Superseded by: none

## Контекст

У проекта должен быть единый источник истины для желаемого состояния инфраструктуры:
версионируемая конфигурация, по которой понятно, что должно быть развёрнуто и как это
изменить. Состояние не должно определяться историей ручных действий в консоли облака.
Создание нового окружения, изменение существующего и переход к другому поставщику
должны опираться на это описание, а не на повторное проектирование инфраструктуры по памяти.

Нужна также переносимость: возможность развернуть эквивалентную инфраструктуру у другого
провайдера, сохранив общий процесс управления и отделив облачные зависимости от приложения.
Инфраструктурные изменения должны следовать общему пайплайну проекта «merge → release»:
изменение рассматривается в PR, а его слияние запускает выпуск в прод.

## Мотивы

- Иметь один источник истины для желаемого состояния инфраструктуры в Git.
- Воспроизводить окружение и переносить его между поставщиками по описанной конфигурации.
- Отделить облачные ресурсы от настройки ОС, приложения и пользовательских данных.
- Проверять действия и стоимость в том же PR, где меняется конфигурация.
- Выпускать инфраструктурные изменения через общий пайплайн проекта «merge → release».
- Использовать стандартный учёт ресурсов и механизм plan/apply.

## Варианты

1. Хранить в Git сценарии с императивными вызовами `yc`/API.
2. Управлять облаком через Ansible и самостоятельно поддерживать учёт ресурсов и diff.
3. Описывать облачные ресурсы декларативно в Terraform и применять рассмотренный plan.

## Решение

Выбран вариант 3. IaC-конфигурация в Git является единственным источником истины для
желаемого состояния управляемой инфраструктуры. Terraform выбран как стандартный механизм
описания ресурсов и их зависимостей, сравнения с фактическим состоянием и применения
изменений. Его providers позволяют использовать тот же процесс для разных поставщиков.
Императивные сценарии потребовали бы самим поддерживать учёт ресурсов, сравнение состояний
и повторяемое применение.

Terraform state связывает конфигурацию с реальными объектами; он не заменяет описание
желаемого состояния. Ручное изменение облака не становится вторым источником истины:
его расхождение рассматривается при следующем plan и явно устраняется либо отражается
рассмотренным изменением конфигурации. Штатные изменения выполняются через IaC.

### Переносимость между поставщиками

При смене облака сохраняется описанный состав и назначение инфраструктуры, а определения
ресурсов адаптируются к provider целевого поставщика. Затем инфраструктура создаётся
обычным plan/apply, ОС настраивается Ansible, приложение выпускается существующим Deploy.
Облачные идентификаторы, адреса и параметры передаются через явную конфигурацию,
не зашиваются в прикладную логику.

Это переносимость подхода и описания, а не обещание применить неизменные `yandex_*`
ресурсы в другом облаке. Типы ресурсов и возможности API зависят от provider;
перед переездом нужно сопоставить сеть, storage, IAM и используемые сервисы.
Terraform создаёт ресурсы, но не переносит автоматически БД, объекты S3, секреты,
внешние DNS-записи и пользовательские данные — для них нужна отдельная миграция.
Универсальный multi-cloud framework заранее не создаётся: достаточно явно отделённой
конфигурации поставщика и существующих границ ОС/приложения.

Terraform управляет облачными ресурсами и необходимыми IAM-доступами. Настройка ОС относится
к [ADR 0063](0063-repeatable-host-configuration.md), выпуск контейнеров остаётся за Deploy.
Мониторинг исключён из текущего восстановления: Terraform не принимает его ресурсы
и не создаёт новый контур наблюдения. Прежние monitoring-ресурсы автоматически не удаляются.

### Хранение и принятие существующих ресурсов

State хранится вне VM в закрытом versioned S3 с проверенной блокировкой. Конфигурация,
версии инструментов и несекретные параметры находятся в Git; Lockbox payload, state
и секретные планы — вне Git. Сохраняемые управляемые ресурсы импортируются;
неизменные зависимости можно сначала подключить по ID и принять под IaC позднее.
Такие внешние зависимости и временно неуправляемые ресурсы перечисляются явно;
наличие ID не выдаётся за описание или воспроизводимость их конфигурации.

### Выкатка облачных изменений

CI строит и сохраняет plan в PR, публикует безопасный diff и оценку стоимости.
Владелец разрешает конкретный CI-run, обязательный check открывает merge.
Merge того же PR автоматически применяет этот сохранённый plan и продолжает необходимые
Ansible/Deploy. Это инфраструктурная часть общего пайплайна «merge → release»,
а не отдельный операционный процесс после слияния. Согласование выполняется до merge;
дополнительный ручной запуск не требуется как следствие выбранного пайплайна.
Новый автоматически одобренный plan после merge мог бы содержать нерассмотренные действия,
поэтому разрешение относится к исполняемому plan.

Используются штатные PR/run/artifact identifiers, защита актуальности ветки и сериализация CI.
Отдельные SHA-манифесты, сравнение SHA ветки с merge-коммитом и собственная очередь
согласований не вводятся. Новый commit/plan требует нового подтверждения.
Неизменённые компоненты не обязаны иметь одинаковый commit SHA.

Оценка использует готовый `terraform-yc-cost-estimation`. Неподдерживаемые ресурсы
перечисляются явно и первоначально оцениваются отдельно по официальным тарифам.
Создание универсального калькулятора не является условием восстановления.

## Последствия

Git хранит проверяемое описание желаемого окружения; создание и изменение ресурсов используют
один процесс. Смена поставщика сохраняет этот процесс и требует адаптации облачного слоя,
проверки эквивалентности сервисов и переноса данных. Наличие Terraform само по себе
не устраняет зависимость от возможностей конкретного облака.

Облачные изменения обозримы до применения и выпускаются по общему правилу «merge → release».
Нужно обслуживать provider/state, ограничивать доступ к планам и выполнять первоначальный
bootstrap backend/identity до штатного процесса. Один окончательный plan рассматривается
и применяется за раз. Реальное изменение state может сделать plan устаревшим: ошибка видна,
новые действия не применяются под прежним разрешением. Merge означает запуск, а не гарантию успеха.

## Проверка

По конфигурации в Git можно определить состав и параметры управляемого окружения;
внешние зависимости перечислены. Создание ресурсов из неё не требует воспроизводить
недокументированные действия оператора. Облачные параметры отделены от кода приложения;
при реальном переезде проверяются план целевого provider и перенос данных, без создания
второго платного облака только ради проверки этого ADR.

Повторный Terraform plan не предлагает необъяснённых изменений, конкурирующий запуск
не получает lock, секретные state/plan не публикуются. Сквозной PR approve → merge
с другим SHA → apply того же файла проходит без перепривязки. Новый commit/plan отменяет
approval; чужой комментарий его не создаёт. Docs-only не меняет облако, app-only не запускает
Terraform, смешанный выпуск ждёт успешного infra apply.
