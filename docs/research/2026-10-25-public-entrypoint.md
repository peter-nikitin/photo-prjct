# Публичный вход для одной VM: статический IPv4 или балансировщик

Дата проверки: **2026-10-25**. Оценка относится к одной минимальной VM FindMe Photo с Nginx/Compose в `core`. По исходным данным адрес `111.88.151.64` зарезервирован в `ru-central1-b`; актуальная привязка адреса и конфигурация облака в этом исследовании не проверялись. Цель — отделить публичный адрес от конкретной VM/её размера, а не обеспечить доступность при отказе единственного приложения.

## Короткий вывод

Для нулевой или небольшой нагрузки и минимальной стоимости **оставить зарезервированный IPv4 непосредственно на VM** — достаточное решение сейчас. Статический адрес сохраняется при остановке VM; для изменения vCPU/RAM VM останавливают и запускают, адрес не требуется менять. Адрес можно отвязать и привязать к другой VM **в той же зоне**. Это требует управляемого переключения и не позволяет перенести сам адрес между зонами доступности. [Адреса VPC](https://yandex.cloud/ru/docs/vpc/concepts/address), [изменение vCPU/RAM](https://yandex.cloud/ru/docs/compute/operations/vm-control/vm-update-resources), [перенос адреса между VM](https://yandex.cloud/ru/docs/compute/operations/vm-control/vm-transferring-public-ip), [ограничение зон](https://yandex.cloud/ru/docs/troubleshooting/vpc/how-to/transferring-ip-to-a-different-zone).

Если принято отдельное требование, что **публичный endpoint должен переживать замену VM или перенос backend в другую зону без смены IP в DNS**, разумен внешний **Network Load Balancer (NLB)**. Его обработчик анонсирует один IPv4 из всех зон, целевые VM меняются через target group; Yandex прямо описывает сохранение публичного адреса при переносе VM в другую зону через обработчик NLB. При единственной VM это не даёт отказоустойчивости приложения, PostgreSQL или данных: если backend нездоров, NLB не имеет другого места для трафика. [Обработчик NLB](https://yandex.cloud/ru/docs/network-load-balancer/concepts/listener), [цели](https://yandex.cloud/ru/docs/network-load-balancer/concepts/target-resources), [миграция зон](https://yandex.cloud/ru/docs/overview/concepts/zone-migration), [health checks](https://yandex.cloud/ru/docs/network-load-balancer/concepts/health-check).

## Что меняется при NLB

| Вопрос | Подтверждённый ответ |
| --- | --- |
| Обязателен новый frontend IP? | **Нет.** Внешний NLB может выбрать заранее зарезервированный статический адрес. Для `111.88.151.64` сначала нужно подтвердить `reserved=true`, владение в нужном каталоге и освободить адрес от текущей VM; назначать его двум ресурсам одновременно нельзя. Возможен короткий разрыв на переключение. Автоматически выделенный адрес не нужен. [Создание NLB](https://yandex.cloud/ru/docs/network-load-balancer/operations/load-balancer-create), [отвязка от VM](https://yandex.cloud/ru/docs/compute/operations/vm-control/vm-detach-public-ip), [миграция зон](https://yandex.cloud/ru/docs/overview/concepts/zone-migration). |
| Как идут 80/443 и TLS? | NLB обрабатывает TCP-порты (например, 80 и 443) и передаёт соединение на target port VM. Это L4-путь: TLS остаётся на Nginx/VM; перенос сертификата в ALB для этой задачи не нужен. Для обоих портов можно задать отдельные обработчики на одном публичном IP. [Обработчик NLB](https://yandex.cloud/ru/docs/network-load-balancer/concepts/listener), [создание NLB](https://yandex.cloud/ru/docs/network-load-balancer/operations/load-balancer-create), [TLS в ALB](https://yandex.cloud/ru/docs/application-load-balancer/tutorials/tls-termination/). |
| Client IP и health checks? | NLB сохраняет исходный IP клиента; правила безопасности VM должны пропускать клиентский трафик и отдельно проверки NLB. Проверки бывают TCP/HTTP; HTTP ожидает `200`. Не прошедший проверку единственный backend оставит сервис недоступным. [VPC security groups](https://yandex.cloud/ru/docs/vpc/concepts/security-groups), [health checks](https://yandex.cloud/ru/docs/network-load-balancer/concepts/health-check). |
| Изменение backend и Terraform? | NLB и target group доступны как `yandex_lb_network_load_balancer` и `yandex_lb_target_group`; target определяется внутренним IP VM и subnet ID. Документация описывает обновление целевой группы без пересоздания обработчика. Сохранение конкретного IP при каждом будущем плане всё равно проверяется по diff. [Ресурс NLB](https://github.com/yandex-cloud/terraform-provider-yandex/blob/master/docs/resources/lb_network_load_balancer.md), [ресурс target group](https://yandex.cloud/en/docs/terraform/resources/lb_target_group), [изменение NLB](https://yandex.cloud/ru/docs/network-load-balancer/operations/load-balancer-update). |
| Исходящий доступ и SSH? | Публичный IP NLB обслуживает **входящий** трафик и не становится egress IP VM. VM без собственного публичного IP для исходящего интернета нужен NAT-шлюз/NAT-инстанс; для SSH из интернета — отдельный маршрут через bastion/VPN либо собственный публичный IP VM. Вариант со вторым IP добавляет его плату; NAT-шлюз тоже платный и не даёт прямого входящего SSH. [Адреса VPC](https://yandex.cloud/ru/docs/vpc/concepts/address), [VM без адреса](https://yandex.cloud/ru/docs/compute/operations/vm-control/vm-change-zone), [тарифы VPC](https://yandex.cloud/ru/docs/vpc/pricing). |

## Цена на 2026-10-25

Для **региона Россия, расчёта в рублях с НДС**, при 720 часах непрерывной работы и без учёта трафика/прочих ресурсов: активный публичный IPv4 — `0,26352 ₽/ч ≈ 189,73 ₽/720 ч`; NLB — ещё `0,92 ₽/ч = 662,40 ₽/720 ч`, плюс обработанный входящий `0,0559 ₽/ГБ`, исходящий `0,0711 ₽/ГБ` и отдельно тарифицируемый интернет-egress. Итого один адрес + NLB: **≈852,13 ₽/720 ч до трафика**, против ≈189,73 ₽/720 ч для прямого IP VM. NLB тарифицируется при обработчике и подключённой непустой целевой группе даже при почти нулевой нагрузке. Если VM за NLB получает второй публичный IP для SSH/egress, прибавляется ≈189,73 ₽/720 ч; если используется NAT-шлюз — `0,39528 ₽/ч ≈ 284,60 ₽/720 ч` и его исходящий трафик. Неактивный зарезервированный IP стоит дороже активного: `0,6039 ₽/ч`. [Тариф NLB](https://yandex.cloud/ru/docs/network-load-balancer/pricing) ([официальная Markdown-таблица, строки 40–43](https://docs.yandex.cloud/ru/ru/network-load-balancer/pricing.md)), [тариф VPC](https://yandex.cloud/ru/docs/vpc/pricing).

**ALB** здесь дороже и избыточен для простого TCP-входа: минимум **2 ресурсные единицы на зону** по `2,63 ₽/единица·ч`, то есть от **3 787,20 ₽/720 ч** в одной зоне без платы за публичный IP и других расходов. ALB имеет смысл лишь при принятом требовании к L7-маршрутизации/терминированию TLS/другим его функциям. [Устройство ALB](https://yandex.cloud/ru/docs/application-load-balancer/concepts/application-load-balancer), [тариф ALB](https://yandex.cloud/ru/docs/application-load-balancer/pricing).

Это сравнение не выбирает платный сервис и не разрешает его создание. Перед любым решением о NLB нужны свежая проверка фактического статуса `111.88.151.64`, применимого договора/валюты и расчёт трафика; затем review точного Terraform plan и стоимости, отдельное одобрение платного изменения. Пока единственная VM остаётся единственной точкой отказа, плата за NLB покупает стабильную точку входа при смене backend, а не HA.
