# 0063: Воспроизводить конфигурацию ОС из кода и выпускать её через общий пайплайн

- Status: Accepted
- Date: 2026-10-25
- Deciders: владелец проекта; явно принял ADR 0056, 0057, 0058 и 0063 в обсуждении 2026-10-25
- Supersedes: none
- Superseded by: none

## Контекст

Конфигурация ОС должна определяться версионируемым кодом, по которому можно одинаково
подготовить пустой хост и привести существующий к нужному состоянию. Это включает
пользователей, доступ по SSH, Docker, mounts и каталоги. Ручные команды и несколько
независимых установщиков делают состояние ОС зависимым от истории действий оператора.
Изменения этой конфигурации должны следовать общему пайплайну проекта «merge → release»,
чтобы принятый код становился конфигурацией работающего хоста.

## Мотивы

- Иметь описание желаемой конфигурации ОС в коде, хранящемся в Git.
- Воспроизводить подготовку и обслуживание хоста одним способом.
- Менять ОС повторяемо, сохраняя существующие данные и сертификаты.
- Иметь одного владельца каждой настройки хоста.
- Отделить обслуживание ОС от выпуска контейнеров и восстановления данных.
- Выпускать изменения конфигурации через общий пайплайн «merge → release».

## Варианты

1. Ручные SSH-команды и отдельные shell/Python-установщики.
2. Cloud-init и замена VM для изменения её подготовки.
3. Ansible для первичной настройки и дальнейшего обслуживания хоста.

## Решение

Желаемая конфигурация ОС описывается кодом в Git и применяется повторяемо.
Для этого выбран вариант 3 — Ansible: он позволяет описывать состояние хоста
стандартными модулями и применять изменения на новой или существующей VM одним способом.
Cloud-init подходит
для первоначальной подготовки заменяемого хоста, но не выбран как основной механизм
дальнейшего обслуживания. Разрозненные установщики потребовали бы отдельно поддерживать
идемпотентность и порядок применения каждой настройки.

### Следствия для реализации

Ansible владеет пользователями, SSH-конфигурацией, пакетами, Docker, mounts, постоянными
каталогами и необходимыми приложению systemd units. Прежние установщики этих же настроек удаляются
после переноса их функций; два владельца одного параметра не сохраняются.

Облачные ресурсы принадлежат Terraform по ADR 0057. Compose/Deploy остаётся единственным
владельцем выпуска контейнеров. Ansible не создаёт второй независимый release entrypoint.
Установка monitoring-агентов и настройка наблюдения отложены отдельной задачей.

### Выкатка изменений ОС

Изменение конфигурации ОС рассматривается и проверяется в PR; после merge CI автоматически
применяет принятую конфигурацию Ansible и проверяет результат. Это этап общего release,
а не отдельная ручная операция обслуживания после слияния.

Изменение только ОС запускает этот этап без обязательного Terraform apply или пересборки
неизменённого приложения. В смешанном изменении сначала применяется требуемая облачная
инфраструктура, затем конфигурация ОС, затем необходимые изменения приложения.
Ошибка настройки или проверки делает release неуспешным; merge сам по себе не доказывает
соответствия работающей ОС принятому коду.

Повторный запуск Ansible сохраняет существующие БД и сертификаты. Restore из дампа
остаётся отдельной разовой операцией с проверкой назначения; выполнение playbook
не является разрешением восстановить данные поверх работающего сервиса.

## Последствия

Подготовка и обслуживание ОС воспроизводимы из Git, а принятые изменения выпускаются
тем же процессом, что и остальные изменения проекта.
Нужно поддерживать playbook и доступ CI по SSH. Check/diff зависит от возможностей
конкретных модулей и не заменяет фактическую проверку после применения.
Используются стандартные модули и небольшой набор задач, без собственного role framework.

## Проверка

Первый запуск подготавливает пустой хост, второй не вызывает необоснованных изменений.
После повторного применения БД и сертификаты сохранены, dump не восстанавливается,
контейнеры не получают второй механизм выпуска. Приёмка ОС не требует monitoring-агентов.
PR только с изменением ОС после merge автоматически обновляет нужную настройку хоста
без ручного SSH-применения, Terraform apply и пересборки неизменённого приложения.
В смешанном release соблюдается порядок cloud → ОС → приложение; ошибка Ansible видна
как ошибка выпуска.
