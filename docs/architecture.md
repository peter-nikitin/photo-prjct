# Архитектура FindMe Photo

## Назначение документа

Концептуальная схема FindMe Photo показывает компоненты, их связи, ответственность
и границы системы. Мотивы решений раскрыты в [ADR](adr/README.md).
Процедуры находятся в [операционных документах](operations.md), статус и свидетельства
работы — в [продуктовом](product-jobs.md) и [инженерном](engineering-jobs.md) реестрах.

## Задача системы

FindMe Photo помогает участникам мероприятий находить снимки по номеру, лицу и данным события,
а фотографам и операторам — загружать и публиковать фотографии. Поиск ограничен мероприятием;
совпадение лица вероятностное, а ручная правка имеет приоритет. Доступ к закрытому оригиналу
зависит от правил галереи и подтверждённой покупки.

<a id="current-architecture--implemented"></a>
## Текущая схема кода

```text
GitHub Actions Infrastructure → Terraform (VPC, диски, одна VM)
                              → Ansible (пользователь, SSH, Docker, PG mount)
                              → подготовленная ОС
GitHub Actions Deploy → immutable образы → Compose (db, web, edge, обработчики)
```

Django — модульный монолит: он владеет HTTP-интерфейсом, полномочиями и правилами продукта.
PostgreSQL — источник истины для состояний и результатов. Object Storage хранит байты медиа.
Обработчики запускаются рядом с Django и обращаются к нему по внутренней Docker-сети. Основу закрепляют
[ADR 0001](adr/0001-django-modular-monolith.md),
[0002](adr/0002-postgresql-system-of-record.md),
[0003](adr/0003-docker-compose-yandex-cloud.md) и
[0017](adr/0017-use-django-polled-photo-processing-jobs.md).

<a id="deployment-domain-assignment--accepted"></a>
## Инфраструктура и развёртывание

Желаемое состояние инфраструктуры и ОС хранится в Git: код служит единым источником истины,
по которому окружение можно воспроизвести и проверить. Изменения проходят общий процесс
PR → merge → release. Этот принцип закреплён в [ADR 0057](adr/0057-declarative-cloud-infrastructure.md)
и [ADR 0063](adr/0063-repeatable-host-configuration.md).

Ответственность разделена по слоям:

- **Terraform** описывает облачные ресурсы: сети, VM, диски и публичный вход. Provider связывает
  конфигурацию с API облака; state учитывает созданные ресурсы и хранится вне VM.
- **Ansible** описывает конфигурацию ОС: пользователей, SSH, пакеты, Docker, mounts и системные
  службы. Один способ настройки применяется и к новой VM, и при дальнейшем обслуживании хоста.
- **Docker Compose и Deploy** отвечают за выпуск контейнеров приложения и обработчиков.
  Настройка ОС и выпуск приложения имеют отдельные границы ответственности.

GitHub Actions связывает эти слои в общий release. В PR проверяются конфигурация, Terraform plan
и оценка стоимости; изменения ресурсов согласуются до merge. После merge автоматически
применяется одобренный plan, затем необходимые изменения ОС и приложения. Для изменения
только одного слоя выполняются соответствующие шаги. Фактический результат проверяется
пайплайном; ошибка применения означает неуспешный release.

Размещение следует принципу минимально жизнеспособной конфигурации: одна VM для PostgreSQL,
Django и обработчиков, отдельный сохраняемый диск БД и Object Storage для медиа. Мощности
увеличиваются по измеренной потребности ([ADR 0056](adr/0056-minimum-viable-infrastructure.md)).
Порядок выпуска описан в [инструкции выпуска](runbooks/deployment.md).

Для независимого от VM публичного адреса используется постоянный IP NLB с TCP forwarding;
TLS завершается на Nginx/Certbot ([ADR 0058](adr/0058-stable-public-entrypoint-nlb.md)).
Nginx направляет запросы приложения к Django. При переносе
сервиса меняется его приватный upstream, при переносе edge — цель NLB; публичный адрес и DNS
сохраняются. SSH использует отдельный служебный доступ к VM. Секреты и SSH-доступ описаны
в [отдельном разделе](#secrets-and-ssh-access).

<a id="observability"></a>
## Наблюдаемость (observability)

Метрики охватывают ресурсы VM, HTTP-запросы Django, доступность БД из приложения, состояние
PostgreSQL, готовую работу очередей и Web Vitals. Сбор, хранение и визуализация разделены:

```text
Linux ────────────────────┐
Django /metrics/ ─────────┤
PostgreSQL → exporter ────┼→ Unified Agent → Remote Write → управляемый Prometheus → дашборд
PostgreSQL → queue-telemetry ┘
  NOTIFY: длительности, две строки БД: остатки импорта
Внешний HTTPS probe ──────→ Remote Write → правила Prometheus → Alertmanager → email / Telegram
```

- **Все метрики проектируются с минимальной нагрузкой и блокировками.** До реализации
  оцениваем стоимость чтений и записей, CPU, памяти и ожидания блокировок. Для накопительных
  измерений используем инкрементальные счётчики; опрос читает готовые агрегаты без пересчёта
  истории и полного обхода задач. Размер буферов, число серий, частота сбора и время ожидания
  ограничены. Сбор не захватывает продуктовые блокировки и не становится условием обработки.
- **Хранение метрик вынесено из VM.** Управляемый Prometheus сохраняет историю независимо от
  замены хоста и не требует содержать локальную базу временных рядов на минимальной VM.
  Unified Agent работает как системная служба: собирает метрики Linux напрямую и опрашивает
  Django, PostgreSQL exporter и коллектор телеметрии очередей. Локальный дисковый буфер сглаживает временную недоступность
  приёмника; сбор ограничен по частоте и ресурсам, чтобы не вытеснять приложение.
- **Метрики не публикуются в интернете.** HTTP-точки Django и exporter доступны агенту через
  loopback, а публичный Nginx закрывает `/metrics/`. Exporter использует отдельную роль БД
  с `pg_monitor`, без superuser и полномочий изменять прикладные данные. Его пароль поступает
  из Lockbox отдельно от пароля приложения. Для Remote Write агент получает IAM-токен через
  metadata service account VM; постоянный ключ облака на хосте не нужен.
- **Владелец очереди определяет границы измерения.** Он передаёт длительности этапов
  после коммита результата, коллектор накапливает агрегаты, мониторинг хранит историю.
  Доли времени рассчитываются за общее окно и показываются вместе с абсолютной длительностью.
  Для архивов `photo_archive` показывает размер очереди, возраст старейшего задания и
  длительности ожидания, сборки ZIP и загрузки в S3. Параллельные пути измеряются отдельно.
  Мотивы решения — в
  [ADR 0067](adr/0067-aggregate-queue-telemetry-from-completion-events.md), протокол и выпуск —
  в [инструкции мониторинга](../deploy/monitoring/prometheus/README.md#queue-telemetry).
- **Остатки всех очередей хранятся в PostgreSQL.** Владелец обновляет счётчики
  незавершённых задач после коммита. Обзор показывает остатки по семействам и состояниям,
  для обработки фото доступен разрез по типу обработчика. Опрос читает только счётчики,
  первичное заполнение и исправление погрешности выполняет оператор.
  [ADR 0078](adr/0078-store-approximate-queue-work-counters.md)
- **Остатки импорта фото хранятся в двух строках PostgreSQL.** После коммита продукта
  Django прибавляет дельты к счётчикам публикации галереи и распознавания лиц.
  Коллектор читает их при опросе. Первичное заполнение и исправление погрешности
  выполняет оператор. [ADR 0072](adr/0072-store-approximate-photo-import-counters.md)
- **Клиентские замеры поступают с публичных HTML-страниц.** Сбор охватывает каталог,
  страницы мероприятий, документы, вход фотографа, корзину и список заказов. При скрытии страницы
  браузер отправляет доступные LCP, INP, CLS и TTFB на тот же домен. Nginx ограничивает размер и
  частоту запросов. Django принимает только тип страницы, класс ширины окна и значения
  метрик, обновляет гистограммы без обращения к БД. URL страницы и cookies не передаются.
  Unified Agent собирает гистограммы через приватный `/metrics/`.
  [Инструкция мониторинга](../deploy/monitoring/prometheus/README.md).
- **Конфигурация наблюдаемости хранится в Git и выпускается по слоям.** Terraform задаёт IAM,
  Ansible устанавливает агент, Compose описывает exporter и коллектор очередей. После применения инфраструктуры
  проверяются свежие сырые серии VM. Ошибка проверки видна в Infrastructure и не блокирует
  выпуск приложения. После выпуска приложения или exporter проверяются серии Django и PostgreSQL
  и соединение exporter с БД.
- **Публикация дашборда независима от доступности источников.** Workflow Monitoring проверяет
  структуру и запросы, обновляет дашборд и читает результат обратно. Совпадающая конфигурация
  не перезаписывается; состояние поступления метрик подтверждают проверки выпуска источников.

- **Уведомления привязаны к нарушению работы.** Правила охватывают внешнюю HTTPS-доступность,
  пользовательские 5xx и задержки, невозможность SQL из Django, критический остаток места на
  системном и PostgreSQL-диске, готовую работу без успешного прогресса. CPU, load и память
  служат диагностике, а не самостоятельному критическому уведомлению. Отсутствие наблюдений
  означает неизвестное состояние; неудачный сбор не подменяется здоровым нулём или отказом.
- **Наблюдение очередей не управляет обработкой.** Ошибки и задержки телеметрии
  изолированы от продуктовых операций. Сбой отправки измерения не откатывает результат,
  недоступность коллектора допускает потерю наблюдений. Сбор не захватывает задания,
  не меняет retry, leases или права обработки.
- **Остатки обработки считаются по уникальным фотографиям.** Подготовка медиа для галереи
  и распознавание лиц — независимые пути; окончательные ошибки входят в соответствующий
  остаток. Оценка обновляется по изменениям состояния и редко сверяется с источником истины
  с ограниченной стоимостью запроса. Для приблизительных значений явно показываем свежесть;
  потерянные события могут временно искажать остаток или оставлять пробелы в длительностях.
  Определения и графики описаны в
  [инструкции мониторинга](../deploy/monitoring/prometheus/README.md#загрузка-и-обработка-фотографий).
- **Правила и маршрутизация выпускаются независимо от приложения.** Workflow Monitoring
  проверяет сценарии через promtool, дожидается свежих источников, заменяет один собственный
  файл правил и проверяет его содержимое и вычисления. Email и Telegram получают также
  восстановление; связанные симптомы группируются. Наличие правила или успешная запись
  конфигурации не считается доказательством доставки получателю.

Внешняя проверка должна выполняться независимо от VM приложения. Предложенный serverless-вариант
описан в [ADR 0065](adr/0065-run-public-probe-as-serverless-function.md); исходный архив функции
передаётся вместе с рассмотренным Terraform plan. Подтверждённое состояние источников, алертов
и доставки находится в [инженерном реестре](engineering-jobs.md).

<a id="photo-ingestion-and-indexing"></a>
## Загрузка и обработка

Фотограф загружает оригиналы в закрытое хранилище; Django принимает их и ставит долговременные
задания. Worker возвращает результат через закрытый API, а Django проверяет и публикует
производные. Решения: [ADR 0013](adr/0013-use-direct-private-object-storage-ingestion.md),
[0017](adr/0017-use-django-polled-photo-processing-jobs.md) и
[0035](adr/0035-use-django-polled-yandex-disk-import.md).

Медиа разделены по назначению согласно [ADR 0068](adr/0068-separate-originals-event-media-and-operational-storage.md).
Браузерные загрузки, промежуточные превью и селфи поиска находятся в приватном бакете временных
файлов. Подтверждённый оригинал публикуется в отдельный приватный бакет в классе `COLD`.
Готовые превью и обложки хранятся в бакете медиа мероприятий в `STANDARD`.
Публичный доступ применяется к обложкам, выдача превью проходит проверку полномочий.
Selfie feedback и Terraform state используют отдельные бакеты.

При CDN-выдаче готовые обложки и превью читаются из Object Storage при промахе кеша.
Подпись CDN защищает доступ к приватным файлам, подпись SigV4 авторизует чтение закрытых
превью в S3. При промахе оригиналы передаёт потоковый маршрут Django, который принимает
запросы с секретным заголовком CDN. [ADR 0069](adr/0069-serve-media-through-cdn-without-imgproxy.md)
Группы источников, CDN-ресурс и правила путей описаны в Terraform. Infrastructure применяет
сохранённый план. При записи правил провайдер переиспользует действующие ключи CDN,
а приложение получает ключи из Lockbox.
[ADR 0073](adr/0073-manage-media-cdn-with-terraform.md)

<a id="search"></a>
## Поиск

Поиск по номеру и лицу ограничен доступными фотографиями одного мероприятия. Django
принимает запросы и контролирует доступ.

Поиск по селфи и поиск по фотографии галереи используют одну очередь в PostgreSQL и общего
фонового исполнителя. Для селфи вектор получает ML-воркер, для фото галереи используется
сохранённый вектор. Исполнитель сопоставляет векторы в PostgreSQL с pgvector. PostgreSQL хранит
задачи и снимки результатов вероятных совпадений. Готовый снимок доступен по ссылке
с токеном. При показе Django проверяет текущую доступность его фотографий. Временный
файл селфи хранится в закрытом Object Storage, его удалением управляет приложение.

[ADR 0019](adr/0019-use-public-event-selfie-search.md) ·
[ADR 0040](adr/0040-use-pgvector-for-exact-face-search.md) ·
[ADR 0066](adr/0066-store-vectors-in-face-search-queue.md) ·
[Алгоритм поиска по лицу](face-search.md) ·
[Эксплуатация очереди](runbooks/gallery-search-queue.md)

Отдельный необязательный этап вычисляет внешность людей на принятом чистом превью:
рамки, качество, ReID, цвет и доступный HOG шлема. Непригодная фигура сохраняет причину
отказа без дескрипторов; фотография и распознавание лиц остаются независимыми.
Флаги `person-appearance-processing` и `apparel-search-expansion` раздельно управляют
постановкой задач и использованием признаков, оба новых gate поставляются выключенными.
Для исторического мероприятия оператор запускает ограниченную партию. Django выбирает
актуальные превью, ставит задачи и выдаёт lease только по списку этой партии. Отдельные
процессы исполняют задачи с обычным авторизованным callback, который сохраняет признаки.
Общий жизненный цикл обработки фото учитывает остаток и длительности этих задач.
Команда оставляет список задач и сверенные с БД исходы для оператора.

В общем исполнителе поиска признаки уверенных лицевых опор могут добавить кадры по
внешности одним ограниченным пакетным запросом. Дополнительные кадры не становятся
новыми опорами. Происхождение и причины veto сохраняются отдельно; рекомендации убрать
совпадение лица по форме не удаляют его автоматически. Выключение расширения сохраняет
обычный поиск по лицу.

[ADR 0074–0077](adr/0074-precompute-person-appearance-on-canonical-previews.md) ·
[Проверка и включение внешности](runbooks/appearance-search.md)

<a id="purchase-and-download"></a>
## Покупка и выдача

Корзина выбирает фотографии, заказ фиксирует состав и цену, а подтверждённая оплата создаёт
право на закрытый оригинал. Возврат браузера с платёжной формы оплату не подтверждает.
Решения: [ADR 0029](adr/0029-use-watermarked-previews-for-paid-photos.md),
[0031](adr/0031-use-orders-and-adapters-for-paid-original-delivery.md) и
[0047](adr/0047-separate-order-payment-from-new-cart-selection.md).

По запросу покупателя или владельца ссылки на бесплатный результат Django ставит подготовку
ZIP для открытой страницы в PostgreSQL. Отдельный `archive-worker` собирает архив и публикует
его в закрытом временном бакете под префиксом `archives/`. Django проверяет доступ при приёме
задания. Случайная ссылка на статус даёт возможность получить короткую подписанную ссылку CDN
до истечения срока архива. При промахе кеша CDN читает ZIP из Object Storage. Готовые архивы
доступны до 24 часов, исходные ZIP удаляются по lifecycle через один день.
Для выпуска нужны права, lifecycle и правило CDN из Terraform, а также место на VM для одного
временного ZIP объёмом до 5 ГиБ. Проверка и откат описаны в
[ADR 0071](adr/0071-prepare-photo-archives-in-background.md).

<a id="secrets-and-ssh-access"></a>
### Секреты приложения и SSH-доступ

Схему секретов приложения, их потребителей и OIDC-идентичность задаёт
[`deploy/environment-secrets.json`](../deploy/environment-secrets.json). Resolver
[`scripts/run-with-environment-secrets.py`](../scripts/run-with-environment-secrets.py) получает
из Lockbox только разрешённый выбранному потребителю набор. Приложение не обращается к Lockbox
самостоятельно. Перечень полей и потребителей поддерживается в manifest без отдельной таблицы
в документации.

Для SSH используются ровно две пары: единая техническая для `deploy` во всех пайплайнах и
административная для `petrnikitin`. Обе хранятся в отдельных Lockbox secrets и устанавливаются
на все Terraform VM. Источники, ожидаемые пользователи и потребители заданы в `ssh_credentials`
общего manifest; получение выполняет тот же resolver, что обслуживает приложение.

Service accounts Infrastructure и приложения имеют `lockbox.viewer` и `lockbox.payloadViewer`
только на техническом секрете. CI не получает административный ключ. Оператор использует свою
учётную запись ЯО. Публичный `INFRA_SSH_PUBLIC_KEY` доступен как repository variable и в
Environment `infrastructure`; административный публичный ключ — в этом Environment.
Приватные ключи не попадают в Git, GitHub Secrets, Terraform state, логи или артефакты;
resolver создаёт файлы `0600` только на время команды и удаляет их после завершения.

Завершение создания VM сверяет её ED25519 host key через стандартные OpenSSH-утилиты с
аутентифицированным serial output и сохраняет открытый ключ в metadata `findme-ssh-host-key`.
Обычные запуски берут текущий IP и сохранённый ключ из структурированного Compute API;
повторное обнаружение не выполняется. Terraform игнорирует только это вычисленное поле.
Процедура оператора — [административный SSH-доступ](runbooks/environment-secrets.md#ssh-keys-infrastructure).
