# Дашборд и критические алерты

Каталог содержит инструменты публикации дашборда и алертов Yandex Monitoring.
Границы компонентов описаны в [архитектуре](../../../docs/architecture.md#observability),
причины общего контракта — в [ADR 0085](../../../docs/adr/0085-unify-operational-queue-observations.md).

## Панели очередей

Каждая очередь имеет собственную панель на существующем дашборде. Все панели создаются
из одного шаблона `queue_panels.py`, поэтому состав, расположение, подписи состояний и
цвета совпадают. Шкала у каждой панели своя. Контейнер и очередь — разные сущности:
несколько исполнителей могут обслуживать один вид работы.

В панели расположены:

| Слева | Справа |
| --- | --- |
| Незавершённые задачи по состояниям | Готово к запуску |
| Возраст старейшей готовой задачи | Завершения в минуту |
| Среднее время по сегментам | Пирог долей времени по сегментам |

Сбои источников отслеживает `QueueObservationUnavailable`. Алерт срабатывает после
пяти минут недоступности по меткам `queue` и `source`, включая исчезновение всех
серий. Пустая очередь и отсутствие завершений при исправном сборе не вызывают алерт.
Остаток разделён на «Ожидает», «Обрабатывается», «Ждёт повтора», «Приостановлено».
Состояние обработки отражает запись задания, а не занятость CPU. Готовность к запуску
показывает доступную сейчас работу; складывать её с остатком нельзя.
Возраст относится к полному текущему циклу старейшей из готовых задач, включая паузы
и повторы. Это отличается от времени ожидания от due time, используемого критическими алертами.

Каталог [queue_catalog.py](../../../src/backend/config/queue_catalog.py) является источником
идентификаторов, русских названий, единиц и сегментов. В нём отдельно представлены
распознавание селфи, два источника сопоставления, шесть обработчиков фото, импорт с Диска,
архивы, письма покупателям и сверки платежей. `selfie_query` не дублируется среди обработки фото.

Чтобы добавить очередь:

1. Подключите у её владельца общий контракт остатков, готовности, исходов и времён.
2. Добавьте описание и конечный набор сегментов в каталог.
3. Проверьте реальные переходы владельца и временные ряды сгенерированных запросов.

При штатном выпуске Monitoring получит новую панель автоматически: каталог и генератор
входят в зависимости классификатора публикации. Ручное копирование JSON-графиков не требуется.
Идентификаторы приборов вычисляются из идентификатора очереди и назначения прибора;
добавление очереди не меняет идентификаторы существующих панелей.

## Сегменты времени

Каждая очередь задаёт собственные сегменты. Например, у архивов отдельно измеряются
ожидание захвата, ожидание места, сборка ZIP и загрузка. У распознавания — ожидание,
получение входа, вычисление, доставка результата и предшествующие попытки.
Точные названия всех сегментов находятся в каталоге и в легендах панелей.

Сегменты не пересекаются и покрывают полное измеренное календарное время успешного цикла.
Предыдущие попытки и интервалы повторов не выдаются за чистое вычисление или простой.
Среднее в секундах считается за скользящие 5 минут, по одной выборке полностью измеренных
успехов для всех сегментов. Успех без достаточных временных отметок входит в скорость
завершений, но не входит в знаменатель средней длительности.

Пирог показывает доли суммарных наблюдённых приращений секунд за выбранный диапазон,
с точностью минутного сбора. Запрос вычисляет приращения между соседними минутными точками, учитывая оба
смещённых опроса, если они попали в один интервал, и наблюдаемый пик перед сбросом.
Визуализация использует `SERIES_AGGREGATION_SUM` по выбранным точкам.
Граница начала диапазона исключает приращение, уже наблюдавшееся до него. При пропуске
опроса следующий прирост относится к моменту следующего наблюдения; подробности событий
внутри пропущенного интервала восстановить нельзя. Нулевые интервалы не создают секторы.

Шаг источника и расчёта пирога — 60 секунд; это часть контракта минутного сбора
[Unified Agent](../../../infra/ansible/roles/monitoring/files/config.yml).
Смена частоты сбора требует согласованного изменения шага и проверки дельт.
При недостатке данных или отсутствии измеренной длительности пирог пуст.
Выбранный период не подменяется последними пятью минутами к его концу.
Режим агрегации поддержан [схемой Yandex Monitoring](https://registry.terraform.io/providers/yandex-cloud/yandex/latest/docs/resources/monitoring_dashboard#visualization_settings).

<a id="queue-telemetry"></a>
## Источники наблюдений

| Наблюдение | Источник | Основные серии |
| --- | --- | --- |
| Остатки | Сохранённые агрегаты PostgreSQL, `findme-queue-telemetry` | `findme_queue_work_count`, `findme_queue_work_available`, `findme_queue_work_observed_timestamp_seconds` |
| Готовая работа | Предикаты владельцев, `findme-http` | `findme_queue_ready_count`, `findme_queue_oldest_ready_age_seconds`, `findme_queue_ready_observed_timestamp_seconds` |
| Результаты | События после коммита, `findme-queue-telemetry` | `findme_queue_results_total`, `findme_queue_duration_observations_total`, `findme_queue_segment_duration_seconds_total`, `findme_queue_results_observed_timestamp_seconds` |
| Подписка | Состояние соединения коллектора | `findme_queue_results_listener_connected` |

Основная метка — `queue`. Остатки также имеют `state`, результаты — `outcome`,
суммы длительностей — `segment`. Возможные исходы: `success`, `failed`, `canceled`.
Повторяемая ошибка не завершает работу. Повторная доставка принятого callback
не должна создавать второй исход. Явный перезапуск терминальной работы создаёт новый цикл.

Отклонённый вход селфи, например непригодное лицо, соответствует неуспешному результату
его владельца; это само по себе не признак аварии инфраструктуры. Корректный поиск без
совпадений и принятое распознавание фото без лиц — успешные результаты.
Частичный импорт считается завершением с ошибками. Успех сверки платежа означает
согласованный авторитетный статус, включая отказ платежа; промежуточный pending
не завершает цикл фоновых сверок. Отмена наблюдается отдельно от ошибки.

Коллектор использует одно существующее соединение LISTEN. Имена очередей и сегментов
задаёт код; события не содержат идентификаторов заданий, email, путей объектов или векторов.
Доставка best effort: без активного подписчика события теряются. Перезапуск процесса
сбрасывает накопительные counters результатов и длительностей. PromQL обрабатывает resets;
история остаётся в управляемом Prometheus. Успех продуктовой транзакции не зависит от
доставки телеметрии.

Ноль, отсутствие измеренных завершений и отсутствие данных различаются. Остатки
приблизительные: их доступность не доказывает отсутствие погрешности. Для каждого
источника проверяется собственная отметка наблюдения, допустимый возраст — 150 секунд.
Устаревшие значения скрываются. Алерт проверяет свежесть каждого источника для
`findme-photo-app`, флаг доступности остатков и LISTEN-подписку. Уведомления
группируются по `incident=queue-observation` и отправляются существующим операторским
маршрутом критических алертов. `alerts.py` добавляет правило из каталога к `rules.yml`.
Проверка Prometheus и публикация используют один и тот же результат генерации.

<a id="queue-work"></a>
## Инициализация и сверка остатков

После первого выпуска новых агрегатов либо при обнаружении погрешности оператор
запускает ограниченную команду на VM в период низкой активности:

```sh
sudo docker compose --project-directory /opt/photo-prjct --project-name photo-prjct \
  --env-file /opt/photo-prjct/.env -f /opt/photo-prjct/docker-compose.deployment.yml \
  exec -T queue-telemetry python /app/src/backend/manage.py rebuild_queue_work_counters
```

До инициализации новый остаток недоступен. Опрос читает готовые агрегаты, не пересчитывает
историю. Ошибки обновлений после коммита и параллельная обработка во время пересчёта
могут оставить погрешность. Команда не изменяет продуктовые задания и не ставит их заново.

После ближайшего опроса выполните `verify_metrics.py queue-work` из окружения инструментов
мониторинга с действующей авторизацией `yc`. Схема источников и проверяемые условия
принадлежат этой команде; наличие JSON-графика не доказывает поступление данных.

<a id="загрузка-и-обработка-фотографий"></a>
## Пользовательские пути

Срок готовности поиска целиком и готовность уникальной фотографии для галереи/распознавания
проходят через несколько очередей. Они остаются отдельными разделами с отдельными
`findme_journey_completed_total` и `findme_journey_segment_duration_seconds_total`.
Не следует складывать остатки задач с количеством уникальных фото или считать одну
фотографию несколькими независимыми фотографиями по числу её обработчиков.
Ошибки готовности фото уже входят в соответствующий остаток.
SQL p75 поиска за 24 часа остаётся отдельной оценкой пользовательского пути.

## Проверка и публикация

Мониторинг разделён на шесть дашбордов:

- **Обзор** — шесть ключевых графиков HTTP, PostgreSQL и ресурсов ВМ.
- **Загрузка и распознавание** — импорт с Диска, шесть обработчиков фото и сквозная готовность фотографий.
- **Поиск и выдача** — распознавание селфи, два поиска, архивы и сквозное время поиска.
- **Коммерция** — письма покупателям и сверка платежей.
- **Web** — Django / HTTP и Web Vitals.
- **Инфраструктура** — ВМ, PostgreSQL, CDN и Object Storage.

На каждом дашборде есть ссылки на остальные. Старые ID и адрес обзорного дашборда
сохраняются. `single-vm-dashboard.json` служит библиотекой существующих графиков;
`dashboard_layout.py` распределяет их и панели очередей по смысловым группам.
Все 121 подробный график сохранены, у каждой из 13 очередей остаются шесть приборов.
Новую очередь необходимо отнести к одной группе; приборы создаются общим шаблоном.

`single_vm_dashboard.py` проверяет все шесть конфигураций через SDK и Promtool.
При первой публикации Monitoring находит дочерние дашборды по постоянным names и создаёт
недостающие через DashboardService. Сначала публикуются подробные дашборды, затем обзор.
Повторный запуск не создаёт копий и не переписывает совпавшую конфигурацию.
Каждое изменение проверяется обратным чтением; ошибка чтения не трактуется как отсутствие.
Публикация не зависит от доступности метрик. Продуктовые процессы и алерты не меняются.

Резервные копии изменяемых объектов сохраняются в artifact `monitoring-backup-<run_id>`
с файлами `overview.json`, `upload.json` и аналогичными именами. При сбое частичной
публикации повторите workflow на той же ревизии. Для отката восстановите прежние
конфигурации из backup через DashboardService Update с актуальным etag; после первого
выпуска новые дочерние дашборды автоматически не удаляются. Простого возврата к старому
монолитному renderer недостаточно для восстановления распределения после последующих выпусков.

Правила и маршрутизация принадлежат `rules.yml`, `alerts.py` и `alertmanager.yml`.
Их проверки не допускают потери прежних условий из-за переименования панельных метрик.

Создание изолированных инструментов из checkout:

```sh
.venv/bin/python -m venv /tmp/findme-monitoring-tools
/tmp/findme-monitoring-tools/bin/pip install -r deploy/monitoring/prometheus/requirements.txt
/tmp/findme-monitoring-tools/bin/python deploy/monitoring/prometheus/single_vm_dashboard.py --validate
```

Для проверки PromQL передайте `--promtool` с путём к Prometheus 3.5.0;
поведенческие сценарии выполняются через `make test-operational`.
Общие проверки и выбор слоёв описаны в [Testing](../../../docs/testing.md).

Порядок последующего выпуска: миграции диагностических полей → приложение, workers и
коллектор → сверка новых агрегатов → свежие источники → Monitoring и read-back.
Историческим заданиям с неизвестными временами не приписываются выдуманные значения.
Откат возвращает контейнеры и сохранённую конфигурацию дашборда. Продуктовые данные
сохраняются, а приблизительные остатки при необходимости восстанавливает оператор.
Открытый PR и успешная локальная проверка не являются доказательством живого выпуска.
